# Codebase layout and conventions

One Rust binary (axum, sqlx + SQLite) serves the JSON API under `/api` and the built React SPA (`web/`). The layout is arranged so that tickets worked on in parallel touch different files. Keep it that way: add files, avoid editing shared ones.

## Commands

| What | Where | Command |
|---|---|---|
| Backend tests (Seam 1 and 2, unit, doctests) | repo root | `cargo test` |
| Lint | repo root | `cargo clippy --all-targets` |
| Frontend build (typecheck + bundle to `web/dist`) | `web/` | `npm run build` |
| Locale key check (en/ru/uk identical) | `web/` | `npm run check:locales` |
| Tests of the locale check itself | `web/` | `npm test` |
| Run locally | repo root | `npm run build` in `web/`, copy `.env.example` to `.env`, then `cargo run` → http://localhost:8095 |
| Frontend with hot reload | `web/` | `npm run dev` (proxies `/api` to the running binary on 8095) |

First time: `npm install` in `web/`. No database setup: the binary creates and migrates the SQLite file on start.

Before reporting a ticket done, run `cargo test`, `npm run build` and `npm run check:locales`.

## Backend map (`src/`)

| Path | Holds |
|---|---|
| `main.rs` | Start-up only: config, database, state, serve. |
| `runtime.rs` | Production wiring: one function per port (`match_source`, `notifier`, `clock`) plus `spawn_background_tasks`. Replace a placeholder inside its own function. |
| `config.rs` | `Config`, read from env. All secrets come from here. |
| `state.rs` | `AppState { db, clock, source, notifier, config }`. |
| `app.rs` | `build_router`: `/api` + SPA fallback. This is Seam 1. |
| `api/<area>.rs` | One file per API area, each with `pub fn router() -> Router<AppState>`. |
| `auth/` | `session.rs`: sessions and the `CurrentUser` extractor. Telegram verification goes in `auth/telegram.rs`. |
| `domain/` | Pure code, no I/O: `model.rs` (canonical Event, Stage, Match, Team, `EventSnapshot`), `ids.rs`, `language.rs`, `user.rs`, and one file per policy (`lock_reveal.rs`, `scoring.rs`, `pickem.rs`, `effective_match.rs`). |
| `ports/` | The three injected traits: `Clock`, `MatchSource`, `Notifier`, with their placeholder production adapters. |
| `store/<aggregate>.rs` | SQL. Plain `async fn`s taking `&SqlitePool`. |
| `sources/` | Data Source adapters (`hltv`, `pandascore`, `liquipedia`) and `fallback`. |
| `poller.rs`, `notifications.rs` | Background work. |
| `testing/` | Test fakes and the Seam 1 harness. Never used by production code. |
| `migrations/` | SQL migrations, embedded at compile time. |
| `tests/` | Integration tests, one file per area. |

Many of these files are stubs holding only a doc comment that names the owning ticket. They exist so a ticket fills in its own file and leaves `mod.rs` alone. A stub may grow into a directory module (`hltv.rs` → `hltv/mod.rs`).

## Adding to the API

1. Put handlers in the area's file, `src/api/<area>.rs`, and register them in its `router()` with paths relative to `/api`:
   ```rust
   pub fn router() -> Router<AppState> {
       Router::new().route("/leagues", post(create)).route("/leagues/{id}", get(show))
   }
   ```
2. A brand-new area needs its own file plus two lines in `src/api/mod.rs` (`pub mod x;` and `.merge(x::router())`). Keep both lists alphabetical.
3. Handlers return `ApiResult<T>` (`src/error.rs`). Take `CurrentUser(user): CurrentUser` to require a session (401 otherwise). Take `State(state): State<AppState>` for the database and ports.
4. SQL goes in `src/store/<aggregate>.rs`, decisions in `src/domain/`. Handlers stay thin: load, call the pure policy, persist, respond.

Rules that hold everywhere:

- **Time** comes from `state.clock.now()`. Never call `Utc::now()` outside `SystemClock`, or tests cannot move time.
- **Errors** are `{"error": {"code": "snake_case"}}` with a fitting status. The server sends no human-readable error text. The SPA shows the translation of `errors.<code>`, so a new code needs a key in all three languages.
- **Not a Member** of a League answers `404 not_found`, the same as a League that does not exist.
- **JSON** uses snake_case fields. Timestamps are RFC 3339 UTC. Ids are numbers.
- **SQL** uses the runtime functions (`sqlx::query`, `sqlx::query_as`), not the `query!` macros, so building needs no database.
- **Vocabulary** in names, routes, JSON and UI text follows `GLOSSARY.md`. One exception: a Match is `game` in Rust names (`game: &Match`, `Inputs { game, .. }`), because `match` is a keyword; JSON and UI still say Match. A Leaderboard row is a `LeaderboardRow` (never "standing"; HLTV's and Liquipedia's own Swiss "standings" tables are their markup, not ours).

## Adding a migration

Add one new file per ticket: `migrations/<NNNN>_<what>.sql`, where `NNNN` is the ticket number times 100 (ticket #4 → `0400_leagues.sql`; a second file from the same ticket → `0401_…`). Parallel tickets therefore never collide on a version number.

- Never edit a migration that is already on `spec-1-kallbet`: sqlx checksums the files and refuses to start on a mismatch. Change the schema with a new migration (`ALTER TABLE …`).
- A migration may rely only on tables from lower-numbered tickets it is blocked by.
- Timestamps are `TEXT`, bound from `chrono::DateTime<Utc>`. Booleans are `INTEGER`. Canonical ids (Event, Match, team) are the HLTV ids, stored as `INTEGER`.
- Foreign keys are enforced (`PRAGMA foreign_keys = ON`).
- Tests pick new migrations up on their own. No registration step.
- Migrations with a lower number than ones already applied still get applied, so merge order does not matter. If a local `kallbet.db` holds a migration your branch lacks, the binary refuses to start: delete the file.

## Writing a Seam 1 test

Create `tests/api_<area>.rs` (its own file, so it conflicts with nobody). Model: `tests/api_dev_login.rs`.

```rust
use axum::http::StatusCode;
use chrono::Duration;
use kallbet::ports::Clock;                     // for app.clock.now()
use kallbet::domain::{EventId, MatchId, StageKind};
use kallbet::testing::{EventSnapshotBuilder, TestApp};
use serde_json::json;

#[tokio::test]
async fn a_prediction_is_rejected_after_lock() {
    let app = TestApp::new().await;                  // fresh in-memory DB, fakes, dev login on
    app.source.put_event(
        EventSnapshotBuilder::new(7148, "Test Major")
            .stage(StageKind::Swiss, "Stage 1")
            .swiss_match(101, (1, 0, 0), "NAVI", "FaZe", app.clock.now() + Duration::hours(2))
            .build(app.clock.now()),
    );
    let alice = app.user("alice").await;             // signed in; keeps its cookies

    app.clock.advance(Duration::minutes(106));       // 14 minutes before the start

    let res = alice.put("/api/…", &json!({ "team_id": 1 })).await;
    assert_eq!(res.status, StatusCode::CONFLICT);
    assert_eq!(res.error_code(), "match_locked");
}
```

What the harness gives you (`src/testing/`):

- `TestApp::new()`, or `TestApp::builder()` with `.dev_login(false)`, `.web_dir(..)`, `.config(|c| ..)`, `.source(arc)` (another source behind the port) or `.source_with(|db, clock| arc)` (one that needs the test's database and clock, e.g. a `FallbackSource` of fakes; model: `tests/fallback_chain.rs`), then `.build()`.
- `app.user("nickname")`: a client signed in as that User (created on first use). `app.anonymous()`: a client with no session. Clients have `get`, `post`, `post_empty`, `put`, `patch`, `delete`. They keep cookies like a browser.
- `TestResponse`: `status`, `json()`, `json_as::<T>()`, `text()`, `header(name)`, `error_code()`.
- `app.clock` (`FakeClock`): `now()`, `advance(duration)`, `set(instant)`. It starts at 2026-01-10 12:00 UTC and only moves when told to.
- `app.source` (`ScriptedSource`): `put_event`, `update_event`, `update_match`, `postpone`, `start`, `finish`, `finish_without_winner`, `cancel`, `fail_with` / `recover`, `alias(stage_id, event_id)` (HLTV's Stage-of-a-Major behaviour), and the call counters `list_events_calls()`, `fetch_event_calls(id)`, `total_fetch_event_calls()`. `ScriptedSource::of(kind)` makes one that reports as another Data Source; wrap it in `ExternalFake::new(arc)` to use it as a fallback adapter (`ExternalSource`) in a `FallbackSource`.
- `app.notifier` (`RecordingNotifier`): `sent()`, `sent_to(user_id)`, `clear()`, `fail_with` / `recover`.
- `app.state`: the same `AppState` the router uses. Use it to drive non-HTTP entry points (a poller step) against the same database and fakes.
- `TEST_BOT_TOKEN`: the bot token in the test config, for signing Telegram login payloads.
- `app.bot("bot-key", "Nickname")`: a client authenticated as that Bot User (registered through `POST /api/auth/bot` with `TEST_BOT_SECRET`, the test config's `KALLBET_BOT_SECRET`); calling it again for the same key issues a new token and revokes the old client's. `app.bearer(token)`: a client that sends `Authorization: Bearer <token>` and has no session. See "Bot Users (ticket #22)".
- `TelegramLogin::new(app.clock.now(), telegram_id, "Name")` (+ `.username()`, `.photo_url()`, `.language()`): builds a signed `POST /api/auth/telegram` body via `.body()`; `.body_signed_with(token)` and `.body_tampered(field, value)` make forgeries. To act as a *Telegram-created* User (instead of `app.user(..)`, which uses the dev login), post that body with `app.anonymous()`.
- `client.cookie(name)` / `client.set_cookie(name, value)`: read or hand a cookie to a client (e.g. replay a session cookie after logout).

Test rules (spec, Testing Decisions):

- Assert what a client can observe: responses, what another Member sees, Points, notifications sent. Do not query the database to check a result.
- Each test builds its own `TestApp`. Nothing is shared, so tests run in parallel.
- Background work must be steppable. Give the poller a method that does one pass based on `clock.now()`; tests advance the clock and call it. Tests never sleep.
- The in-memory database has a single connection. Do not hold a transaction open while awaiting another query on the pool: it deadlocks.

Seam 2 (parser) tests keep fixtures under `tests/fixtures/<source>/` and feed them to the pure parser. No network. Fixtures are real saved responses, never hand-written; list each one with its provenance in `tests/fixtures/<source>/README.md`. A test may derive a broken variant from a real fixture in code (e.g. a renamed class) to check that changed markup is an error.

## Data Sources

- Every adapter implements `MatchSource` and returns `SourceError::Parse` for anything it does not understand, never empty data. `Unavailable` is for network, browser, Cloudflare and HTTP failures.
- `fetch_event(id)` may return a snapshot whose `event.id` differs from `id`: HLTV gives each Stage of a Major its own event id, and the canonical Event is the Major (the parent HLTV event). Store and key by `snapshot.event.id`.
- Team logos are never sent to the SPA as Data Source URLs (`Team::logo_url`). The SPA shows `/api/teams/{id}/logo`; the HLTV adapter downloads each logo once (`sources::hltv::LogoCache`).
- HLTV adapter: `sources::hltv::HltvSource::new(Arc::new(ChromePages::new(url)), clock).with_logos(LogoCache::new(dir))`. Its pure parser is `sources::hltv::parse`. `tests/hltv_live.rs` runs it against a real browser and HLTV (ignored by default; see the file for how to run it).

## Fallback chain (ticket #9) — read before #10, #11, #13

`state.source` in production is `sources::fallback::FallbackSource` (`runtime::match_source`): HLTV → PandaScore → Liquipedia, one circuit breaker each. Callers just use `MatchSource`; nothing else changes.

**Writing a fallback adapter (#10, #11).** Implement `sources::fallback::ExternalSource` in your own file (`sources/pandascore.rs`, `sources/liquipedia.rs`). Both already hold a placeholder type (`PandaScoreSource::new(token)`, `LiquipediaSource::new()`) that answers `NotConfigured` and is already wired into the chain in `runtime::match_source`: replace its body, keep the type (add constructor arguments if you need them, e.g. a `Clock` for rate limiting, and adjust that one call in `runtime.rs`). You never produce canonical ids yourself:

- `kind()` → your `DataSourceKind`.
- `list_events()` → `Vec<ExternalEvent { external_id, canonical: Option<EventId>, name, starts_at, ends_at }>`.
- `find_events(&EventHint { id, name, starts_at, ends_at })` → candidates for the canonical Event (search by name/dates, return a few; empty if nothing is close). `name` is empty when the Event was never stored (HLTV was down when the League was created): then only a candidate with `canonical == Some(id)` is accepted, so search by HLTV id if your source can. Called only until the Event is mapped.
- `fetch_event(external_id)` → `ExternalSnapshot { event, stages: Vec<Stage>, matches: Vec<ExternalMatch> }` for the **whole** Event (every Stage of a Major). `ExternalMatch { external_id, canonical: Option<MatchId>, stage (an ordinal of your own `stages`), placement, team_a/team_b: Option<ExternalTeam { external_id, name, canonical: Option<TeamId> }>, format, scheduled_start, actual_start, status, winner: Option<Side::A|B>, score }`, score in your record's team order.
- Errors as for `MatchSource`: `NotConfigured` (skipped, not a failure), `Unavailable`, `Parse` (both count for the breaker), `NotFound`.
- Put an id your data carries in `canonical` (Liquipedia: a Match template's `hltv=` → `ExternalMatch::canonical`, an infobox HLTV event link → `ExternalEvent::canonical`); it links directly, bypassing name/time matching.
- Parser tests are Seam 2 as usual (fixture → `ExternalSnapshot`). "Records are mapped to canonical ids through the mapping table" is the chain's job and already tested in `tests/fallback_chain.rs`; to check your adapter end to end, compose it in a `FallbackSource` like that file does.

**How the chain behaves** (`sources/fallback/mod.rs`, pure rules in `mapping.rs`):

- `fetch_event(id)`: first resolve aliases (an HLTV Stage event id that HLTV once answered with its Major is stored as an `hltv`/`event` mapping, so a pasted Stage link keeps resolving to the Major while HLTV is down). HLTV answers → its snapshot is returned unchanged; `NotFound` from HLTV ends the search. Otherwise each fallback in order: find its Event (mapping, else `find_events` + `mapping::choose_event`: carried HLTV id, else best name similarity ≥ 0.4 with overlapping dates, ambiguous = none), fetch, link, merge. All fail → `Unavailable` if any source failed, else `NotFound`, else `NotConfigured`.
- **Breaker**: `NotConfigured` never counts; `Unavailable` and `Parse` count; `NotFound` counts as a success. After `KALLBET_BREAKER_FAILURES` (3) in a row the source is skipped for `KALLBET_BREAKER_OPEN_MINUTES` (15), then tried once (half-open: exactly one call goes through, concurrent ones are refused until it reports back): success closes it, failure reopens it. Time comes from `Clock`. This is the poller's back-off. In-memory, per adapter, two per adapter: one for `fetch_event`, one for `list_events`/`find_events`, so a working Event list does not reset the count of failing Event pages (tests: `tests/fallback_breaker.rs`). An HLTV parse error is a failure like any other, so the chain falls through to fallbacks. A Swiss Match drawn in the chart but in neither team's standings rows (as during a live round) is not an error: the parser leaves it out of that snapshot, and the stored Match stays as it was (in only one team's rows is still an error). This is checked on a fixture derived from a real page; no real page with a live Swiss round has been saved yet, so the real markup of that state is unverified.
- **Linking a record**, first hit wins: manual mapping → id carried by the record → earlier automatic mapping → matching. Teams match by normalised name (`fallback::names::team_key`: lowercase alphanumerics without "team", "esports", "gaming", "clan", ...), this Event's teams first, then all teams. A Match matches a stored Match of the same Stage (the record's Stage mapped by kind and position) by teams and Scheduled Start within ± `KALLBET_MATCH_WINDOW_HOURS` (6); one agreeing team plus the time suffices, and the other team is then inferred and mapped (unless another record of the same snapshot is that team). Every link is stored in `external_ids` (origin `auto` / `source`).
- **Unmatched** (Event has HLTV data): a record with a team that cannot be linked, with no teams, or with a team pair that already meets in that Stage at another time, is left out and flagged in `unmatched_records` (kinds `match` and `team`; `event` with an empty external id when no Event fitted). Flags are replaced per (Event, source) on each fetch from that source, so a fix clears its flag on the next fetch. A Match whose two teams are linked but which is not stored yet (a new Swiss round while HLTV cannot parse it) is **added** with a local id.
- **Merge rule** (lower priority never spoils higher priority): a fallback updates only the progress fields of a stored Match (Scheduled Start, actual start, status, winner, score), fills teams still TBD, and keeps Stage, placement, format and HLTV team names; it never moves a Match backwards (finished → live → upcoming); a record whose winner is not one of the stored Match's two teams (a linked record whose source changed a team) is flagged as unmatched and not merged; it never touches a Match a higher-priority source has settled (finished/cancelled) — a different winner there is recorded as a conflict and the stored result stands. A settled result from a lower-priority source is overwritten by a higher one (HLTV always overwrites), with a conflict when the winner differs. Stored Matches a source does not report are left as they are (`save_snapshot` never deletes). The merged snapshot contains only what that source may write, and its Matches get `source` = that source.
- **Conflicts** (`source_conflicts`): `{match_id, kept_source, kept_winner, other_source, other_winner (NULL = Void), detected_at}`, keyed by (match, other source); kept even if the sources later agree.

**Ids of Matches not on HLTV (decision; #13 uses it too).** Canonical ids stay HLTV's positive `i64`s; a Match or team with no known HLTV id gets a **negative local id** (-1, -2, ...) from `store::external_ids::allocate_local_ids(db, IdKind::Match | Team, count)` (returns the first; the rest count down). #13: take a hand-added Match's id from there. When a fresh HLTV snapshot shows a local Match (same teams by name, or one team plus the time, within the window; both teams in the same Swiss or Playoffs Stage at any time, since a pair meets once there), the chain re-keys it to the HLTV id before the poller saves the snapshot (`rekey_match` / `rekey_team`: matches, predictions, match_locks, picks, conflicts, mappings), so Predictions follow. **Any new table with a match or team id column must be added to `rekey_match` / `rekey_team`** (#13 added `overrides` and the `notification_log` keys). Hand-added Matches (#13) are never re-keyed: they are League data outside `base_view`, see "Overrides (ticket #13)".

**HLTV down and the Event never fetched from HLTV**: if the Event row exists (from an earlier HLTV Event list, or a League), fallbacks find it by name and dates; its Matches and teams get local ids (nothing to link to), and are adopted when HLTV returns. If nothing is known but the id, only a fallback whose candidate carries that HLTV id can serve it; otherwise League creation answers 502 `source_unavailable` and the user retries. `list_events` falls back the same way but only returns Events it can link to a canonical id (mapping, carried HLTV id, or a stored Event matched by name); others are dropped.

**For #13 (store functions, `store/external_ids.rs`)**: `unmatched(db, event) -> Vec<UnmatchedRecord { source, kind, external_id, description, seen_at }>`, `conflicts(db, event) -> Vec<SourceConflict>`, and the fix `set_manual(db, source, IdKind::Team | Match | Event, external_id, canonical_id, now)`: a manual row is never overwritten automatically and wins over every other link from the next fetch on. These are base-data fixes (they apply to every League on the Event). #13 decided League Admins do **not** get `set_manual` (spec story 76): they see `unmatched`/`conflicts` read-only (`GET /api/leagues/{id}/data-warnings`) and fix their own League with a teams Override.

**PandaScore adapter (#10)**: `sources/pandascore/` (`parse.rs` pure parser, `mod.rs` REST fetch with `PandaScoreSource::new(token)` / `with_base_url`). No token (or an empty one) → `NotConfigured` before any request. Token goes in the `Authorization: Bearer` header; errors never contain it. Serie = Event (name = league name + serie `full_name`, e.g. "IEM Cologne Major 2026": the serie alone is "Cologne Major 2026" or just "Season 14 2026"), tournament = Stage. Stage kind (`parse::stage_kind`, from real captures): `has_bracket` → Playoffs unless the name says group/play-in (a real round-robin "Group Stage" has `has_bracket: true`); no bracket and a Swiss name ("Stage <n>", "Opening/Elimination Stage", "Challengers/Legends Stage") → Swiss; else Groups. The Swiss round is in the match name ("Round 5: NRG vs BIG"); the record bucket is replayed from results in Scheduled Start order (equal records `w`-`l` → bucket `w`-`l`, round `w+l+1`, which must agree with the name; round 1 is always 0-0; a TBD team, unequal records or a disagreeing name → `Unplaced`). Playoffs slots come from `previous_matches` of `/tournaments/{id}/brackets` (single-elimination tree only, else `Unplaced`; siblings are ordered by the number in their names because the listed order is not top to bottom). The fetch layer reads `/brackets` only for Playoffs Stages and uses `page[size]`/`page[number]` and plain-date `range[begin_at]` (the forms the real API answered 200). `/series/{id}/tournaments` embeds slim matches (no opponents/results): not used. `postponed` → Upcoming with no Scheduled Start; `canceled` without a forfeit → Cancelled. Verified against real captures of 2026-11-22 (Cologne Major, Singapore Major, Elisa Open Suomi); still unverified: running/postponed/canceled/forfeit matches (constructed only), real matches of Stages 2 and 3, double-elimination `/brackets`, paging beyond page 1. See `tests/fixtures/pandascore/README.md`. Tests: `tests/pandascore_parser.rs` (Seam 2), `tests/pandascore_source.rs` (fetch layer against a local server).

Tests: `tests/fallback_chain.rs` (fallback on failure, order, breaker open/half-open/close, unconfigured skipped, carried ids, unmatched flags, manual mapping, conflicts both ways, no rollback, local ids and adoption with Predictions, never-fetched Event, Stage link). Unit tests for names in `sources/fallback/names.rs`.

## Liquipedia adapter (ticket #11)

`sources/liquipedia/`: `LiquipediaSource::new(clock)` (production; `::with(wiki, pause, clock)` for tests), `parse.rs` (pure, Seam 2), `wikitext.rs` (template reader), `limiter.rs` (rate limits). Tests: `tests/liquipedia_parser.rs` (fixtures in `tests/fixtures/liquipedia/`, README has provenance), `tests/liquipedia_source.rs` (limits, headers, failures, and the adapter inside a `FallbackSource`), `tests/liquipedia_live.rs` (ignored, real API).

- **API rules** (<https://liquipedia.net/api-terms-of-use>): at most 1 request per 2 s; `action=parse` at most 1 per 30 s (never used); custom User-Agent `KallBet/0.1 (https://kallbet.kulunchick.tech)`; gzip; cache. `limiter::RateLimiter` books slots from the injected `Clock`; the waiting goes through the `Pause` port (tests move a fake clock, nothing sleeps). `expandtemplates` is held to the 30 s class too. A wait over 60 s fails as `Unavailable`; a 429 backs off for `Retry-After` (default 2 min), a 403 for 10 min. `reqwest` gained the `gzip` feature.
- **Event id** = the root page title (`Intel Extreme Masters/2026/Cologne`). `fetch_event` = `list=allpages` (Stage subpages) + one `action=query` for all pages + at most one `expandtemplates` for team keys not yet known (names are cached for the process). Stages come from `{{SwissStandings}}` (Swiss) and `{{Bracket|Bracket/N}}` with N a power of two (Playoffs); any other bracket (double elimination) is a `Groups` Stage with `Unplaced` Matches, like HLTV's. A Matchlist-only page yields no Stage.
- **What is derived**: winner from map round totals (overtime included) or `score=W`; Swiss record from the High/Mid/Low Matchlist order of each Round (a different count of lists is a `Parse` error); format from the number of `mapN` slots; times from `{{Abbr/CEST}}`-style zones (unknown zone, e.g. `CST`, is a `Parse` error); `Live` = unfinished and started less than 12 h ago, or a map already played. `hltv=` goes to `ExternalMatch::canonical`. Empty TBD slots with no teams and no `hltv=` are left out. Team external id = template key; names via `{{Team|key}}` (not `{{TeamName}}`).
- **Not done**: `list_events` answers `NotConfigured` (the lists are Lua-generated, only reachable through `action=parse`); `find_events` searches by the HLTV name and keeps pages with an `Infobox league`, so it needs a stored name. No cancelled/postponed state (never seen on a page). No `canonical` Event or team ids (Liquipedia pages carry no HLTV Event id).

## Frontend map (`web/`)

| Path | Holds |
|---|---|

| `src/pages/<area>/` | The area's pages, components and API calls (`api.ts`). |
| `src/locales/<lang>/<namespace>.json` | Translations, one namespace per area. Loaded automatically by `src/i18n/index.ts`. |
| `src/components/` | Shared pieces: `Logo`, `LanguageSwitcher`, `HeaderUser` (the header's User corner), `ServerStatus`, `Avatar` (a User's avatar, initial as fallback), `TeamLogo` (a team's logo from `/api/teams/{id}/logo`, nothing when it has none), `Medal`. |
| `src/app/Layout.tsx` | Header, page outlet, footer. |
| `src/api/client.ts` | `api<T>(path, {method, body})`, `ApiError` (`status`, `code`), `errorMessage(t, error)`. |

Adding a page: create `src/pages/<area>/routes.tsx` and its locale namespace in all three languages. Neither the router nor the i18n setup needs editing.

```tsx
// src/pages/leagues/routes.tsx
const routes: RouteObject[] = [{ path: "/leagues", element: <MyLeaguesPage /> }];
export default routes;

// in a component
const { t } = useTranslation("leagues");   // src/locales/<lang>/leagues.json
```

Locales:

- Every namespace file exists for `en`, `ru` and `uk` with the same keys; `npm run check:locales` fails otherwise. Plural forms (`key_one`, `key_few`, `key_many`, `key_other`) count as one key.
- Put an area's strings, including its `errors.<code>` texts, in the area's own namespace. `common.json` is shared and therefore a merge hotspot: add to it only for strings used across areas.
- No user-visible string is hard-coded in a component.

## Leagues and membership (ticket #4)

- **Gate every League-scoped endpoint** with `api::leagues::require_member(&state, &user, league_id)` (404 `not_found` for non-Members and missing Leagues) or `require_admin` (adds 403 `forbidden`). Both return the `store::leagues::League` and the caller's `Membership`.
- **Membership is a stretch of time**: table `memberships` has `joined_at` and `left_at` (NULL while current). Leaving sets `left_at`; joining again inserts a new row. `store::leagues::all_memberships(db, league)` returns every stretch, for the Eligible Member rule. `store::leagues::members` lists current Members only. At most one current row per User per League (partial unique index). #12's kick should call `end_membership`.
- Roles are `domain::Role` (`member`, `admin`). The creator is `leagues.creator_id` and also an admin Member; the creator cannot leave (409 `creator_cannot_leave`).
- The `events` table (0400) holds only id, name and dates, upserted from `MatchSource::fetch_event` when a League is created. #5 adds Stages, teams and Matches in its own migration and fills `store/events.rs`.
- Invite Link: the secret is `leagues.invite_token`; the SPA link is `/join/<token>`. API: `GET /api/invites/{token}` (preview) and `POST /api/invites/{token}/join`; an unknown or reissued token is 404 `invite_invalid`. Only admins receive `invite_token` in the League JSON.
- Data Source failures reach clients as 502 `source_unavailable` (`api::events::source_error`).
- Frontend: the header (`HeaderUser`) links to `/leagues`. `/join/<token>` signed out shows a sign-in prompt linking to `/login?next=/join/<token>`; `LoginPage` honours `?next=` (same-site paths only) after any sign-in, so pages can send visitors through login and back the same way.

## League management (ticket #12)

- Endpoints (all gated by `require_admin` unless noted): `DELETE /api/leagues/{id}/members/{user_id}` (kick = `end_membership`; 409 `creator_protected` for the creator, 409 `use_leave` for yourself, 404 when the target is not a current Member), `PUT /api/leagues/{id}/members/{user_id}/role` (`{"role": "member"|"admin"}`, 204; creator is 409 `creator_protected`), `POST /api/leagues/{id}/delete` (creator only: 403 for other Members, 422 `confirmation_mismatch` unless `{"confirm_name"}` equals the League name).

Every later table that references a League (directly, or through `memberships`) must declare `REFERENCES leagues (id) ON DELETE CASCADE` (or cascade from another table that does), as `memberships` does. Never reference `leagues` without a cascade, and do not add a hand-written delete step per table. Tests: delete a League that has your rows and check they are gone through the API.
- **Rule for #5 and #13 reviewers: no API path lets anyone create or change another Member's Prediction.** A Prediction handler takes the User only from `CurrentUser`, never from the path or body, and writes only for that User. No admin/creator override exists. The test is `tests/api_prediction_ownership.rs` (#6); extend it when adding any Prediction-writing route.

## Matches, Lock and the poller (ticket #5)

How League logic gets its Matches — read this before #6, #7, #13, #14, #16, #17:

- **One entry point**: `league_matches::evaluate(db, &league, now) -> LeagueMatches`. It loads the League's **effective Match view**, its membership stretches, all its Predictions and stored stamps, runs the Lock/Reveal policy for every Match, **persists new stamps**, and returns `{ view, outcomes, predictions, members, profiles, … }`. The Matches API, the Prediction endpoint and the poller all call it. Never read `store::events::base_view` (raw source rows) from League logic.
- **Effective Match view**: `domain::effective_match::effective_view(base, &LeagueOverrides) -> EventView` is pure and applies the League's Overrides (see "Overrides (ticket #13)"). `EventView { event, stages, teams, matches: Vec<SourcedMatch { data: Match, source, updated_at }> }`. Hidden Matches drop out of `matches`; hand-added ones are appended.
- **Lock/Reveal policy**: `domain::lock_reveal::evaluate(&Inputs { game, members, predicted, stored, now }) -> Outcome { stamps, lock_time, transitions }`. Lock = earliest of Scheduled Start − 15 min (only once both teams are known; TBD Matches do not Lock by schedule), actual start (or "now" if started without a time) and cancellation, once it is ≤ now. Once every Eligible Member has predicted (or the Match starts or cancels), stored stamps never change; if an `Upcoming` Match is postponed back open while a human Eligible Member missed predicting (or zero Predictions exist), `Transition::Unlocked` clears the Lock row, and if all humans predicted but a Bot User missed Hard Lock, `Transition::HardUnlocked` clears only `hard_locked_at`. `members` (every `MemberSpan { user_id, joined_at, left_at }`) and `predicted` (users with a Prediction) drive Reveal (#6, see below); `Outcome.eligible` lists the Eligible Members. `store::predictions::record` persists transitions with COALESCE and handles `Unlocked` / `HardUnlocked`.
- **Schema** (`migrations/0500_matches_and_predictions.sql`): `stages`, `teams`, `matches` (base data; `placement_kind` + `swiss_*` / `playoff_*` columns; `source`, `updated_at` = last successful poll), `polls` (cadence bookkeeping), `predictions (league_id, match_id, user_id, team_id, updated_at)`, `match_locks (league_id, match_id, locked_at, revealed_at)`.
- **Poller** (`poller.rs`): `poller::tick(&state)` is one pass at `clock.now()`; production runs it every 20 s (`runtime::spawn_background_tasks`). Order: evaluate every active League (stores Locks due by the data we had, before a postponement can move them) → poll the Event list (6 h; stored in `event_list` by `poller::refresh_event_list`, and `GET /api/events` serves that copy, asking the source only while nothing is stored yet) → poll each Event with a non-archived League (5 min, 1 min if a Match is live or starts within 45 min, by the source's data or any active League's effective view without hand-added Matches, so a Scheduled Start Override counts) → evaluate every active League again and call `after_poll(state, league, matches, now)`. **#7, #16, #17 each add one call inside `after_poll`.** It runs on every tick, not only when data changed, so make those hooks idempotent (scores recomputed, notifications deduped). A Match first seen live without a source `actual_start` gets `now` stamped.
- **API**: `GET /api/leagues/{id}/matches` → `{ event, stages: [{ ordinal, kind, name, groups: [{ kind: "record", wins, losses | kind: "playoff_round", rounds_before_final | kind: "unplaced", matches: [MatchCard] }] }] }`. `MatchCard` (`api/matches.rs`) has `team_a/team_b {id,name}|null`, `format`, `bracket_slot` (Playoffs slot within its round, else `null`), `scheduled_start`, `actual_start`, `status`, `winner`, `score`, `lock { locks_at, locked_at, locked }`, `my_prediction`, `source`, `updated_at`. It also has `predictions` (#6) and `my_result`/`my_points` (#7), see their sections; build fields from `LeagueMatches` in `view_for`. Never put other Members' Predictions in it before Reveal.
- `PUT /api/leagues/{id}/matches/{match_id}/prediction` `{team_id}` → `{match_id, user_id, team_id, updated_at}`; errors 404 `not_found`, 409 `match_locked`, 422 `team_not_in_match`. It evaluates before (reject if locked) and after the upsert (where #6's Reveal on the last Prediction fires). #17 adds the archived check here.
- **Writes that depend on Lock are one write transaction** (ADR-0003). A Prediction, a Pick'em, every Override write and the poller's save of a fetched snapshot open `db::begin_write(&state.db)` (`BEGIN IMMEDIATE`), read `state.clock.now()` only once it is open, call `league_matches::evaluate_in(&mut tx, ..)` (stores every Lock due by the data as it is), check, write, evaluate again and end with `db::finish(tx, result)` (commits on success and on 4xx, so stamps stored by the evaluation are kept). The Prediction and Pick'em store writes are also conditional on no stored Lock (`predictions::upsert` returns `None`, `pickems::save` returns `false`; a Bot User's `upsert_for_bot` / `save_for_bot` are conditional on no stored Hard Lock). Never move a Scheduled Start (Override, snapshot) without evaluating the League at the current clock first in the same transaction. Inside the transaction use only the transaction's connection: the in-memory test pool has one connection, so a pool query deadlocks. Tests: `tests/lock_atomicity.rs` (interleavings driven through store functions and a slow fake source).
- **Pick'em (#14)**: a Stage's Matches and its first start come from `LeagueMatches.view` (`EventView::matches` filtered by `data.stage`); its Hard Lock is the Stage's first Match starting, and the humans may Lock it earlier (see "Pick'em").
- **SPA**: `/leagues/:id/matches` (`web/src/pages/matches/`). `MatchCard.tsx` renders `PredictionsLine.tsx` (#6); #7's ✓/✗ goes next to the score; team logos via `TeamLogo`. A Playoffs Stage is drawn as a bracket (`PlayoffsBracket` in `MatchesPage.tsx`); the layout and the card state (a Void Match is cancelled or finished without a winner, and says so with a visible badge, never "Finished") are pure functions in `layout.ts`, tested by `web/scripts/matches-layout.test.mjs` (`npm test`). Strings in the `matches` namespace. The League page links to it.
- Local manual testing: the production `MatchSource` is the fallback chain (#9). Without `KALLBET_CHROME_URL` (and until #10/#11 land) every source is skipped, so a fresh League shows no Matches unless the DB is seeded by hand.

## Reveal (ticket #6)

- **Rule** (`domain::lock_reveal::evaluate`, ADR-0003): while open, if every Eligible Member has predicted (and there is at least one), the Match Reveals and Locks at that instant (`Locked(now)` + `Revealed(now)`). Since #22 that means every *human* Eligible Member, and the Lock binds the humans; see "Bot Users (ticket #22, spec #21)". Otherwise it Reveals at Lock, stamped with `locked_at`. A stored Lock without a Reveal (data from before #6) is Revealed at its Lock on the next evaluation. Once every Eligible Member has predicted, stamps are never cleared; a postponed `Upcoming` Match with missing Predictions emits `Transition::Unlocked` (or `Transition::HardUnlocked` for a Bot User).
- **Eligible Members** (`lock_reveal::eligible(members, locked_at)`): current Members (`left_at` NULL) whose current stretch began at or before `locked_at`; while open, every current Member. So leaving or being kicked removes a Member at once (the next evaluation may Reveal: any later API call or poller tick does it), and a Member who joins, or rejoins, after Lock does not count. N counts only Eligible Members' Predictions.
- **API**: `MatchCard.predictions = { count, eligible, revealed_at, revealed }`. `revealed` is `null` before Reveal and then `[{ user_id, nickname, avatar_url, team_id }]` for the Eligible Members who predicted. It is built only in `api::matches::predictions_view`; it is the only place other Members' Predictions leave the server. `LeagueMatches.profiles` (current Members with Nickname/avatar) feeds it.
- **For #16 (Reveal announcement exactly once)**: the moment of Reveal is `match_locks.revealed_at`, exposed as `LeagueMatches.outcome(id).stamps.revealed_at`. A Reveal can be stored by any caller of `league_matches::evaluate` (the Prediction endpoint fires the early one), so do not rely on seeing `Transition::Revealed` in `after_poll`. Instead, in `after_poll`, announce every Match whose `stamps.revealed_at` is set and dedupe through the notification log with a key such as `reveal:<league>:<match>`; skip ones revealed long ago (e.g. `now - revealed_at` over a few hours) if old data must not trigger a burst.
- Tests: `tests/api_reveal.rs` (each rule, the no-leak check, Lock and Reveal per League); `tests/api_prediction_ownership.rs` (#12's rule).
- SPA: `web/src/pages/matches/PredictionsLine.tsx` shows "N of M predicted", then avatars split by team. `MatchesPage` reloads after a Prediction so a Reveal it triggered shows at once.

## Pick'em (ticket #14; #15 adds the Playoffs variant)

- **Stage ordinals can change** when HLTV returns with a Stage a fallback did not list: `store::events::save_snapshot` then moves everything kept by ordinal (`pickems`, `picks`, `pickem_locks`, hand-added `matches`) to the new ordinal, read from the stored Matches the snapshot places elsewhere (`move_stage_data`). **A new table keyed by Stage ordinal must be added there.**
- **Storage is shape-generic** (`migrations/1400_swiss_pickem.sql`): `pickems (league, stage_ordinal, user)` + `picks (…, kind, slot, team_id)` (cascade from `leagues`), `pickem_locks (league, stage_ordinal, locked_at, hard_locked_at)` (`hard_locked_at` is from `2201_pickem_hard_lock.sql`) and `pickem_edit_windows (league, stage_ordinal, user_id, ends_at)` (`1100_pickem_edit_windows.sql`, the final edit window). Swiss kinds: `three_nil`, `zero_three`, `advance` (slot = list position). **#15: use kind `bracket`, slot = bracket slot**; a team may repeat across slots, so team uniqueness is a domain rule, not a constraint. `domain::pickem::{Pick, PickKind}` already has `Bracket`.
- **Domain** (`domain/pickem.rs`, pure, reads the effective view only): `SwissPickem::{validate, to_picks, from_picks}`, `swiss_teams`, `swiss_outcomes`, `score_swiss`; shared by every shape: the Lock policy `evaluate_lock(&LockInputs) -> Stamps { locked_at, hard_locked_at }` (with `hard_lock_due` and `expected_lock`) and `rank` (shared places, 1-1-3). #15 added its own `BracketPickem` validate/score next to them and reuses the Lock policy and `rank`.
- **A Stage's team list**: a Swiss Stage's round 1 contains all its teams, so `swiss_teams` is the teams of its round-1 Matches (all Matches of the Stage if the Data Source gives no round numbers). It is known from the first poll, long before later rounds are paired. For the Playoffs the candidates are the teams of the paired bracket slots; later slots are filled by the picker's own earlier picks (#15 decides how to treat TBD first-round slots).
- **Lock**: two stamps per League and Stage in `pickem_locks`, each stored once and never cleared. The pure policy is `domain::pickem::evaluate_lock`; `store::pickems::evaluate_lock` loads its inputs, stores a new stamp and returns a `StageState`. `league_matches::evaluate` calls it for every Swiss and Playoffs Stage, and so do the Pick'em GET, PUT and Leaderboard, so the poller stamps both and a later postponement cannot reopen either.
  - **Hard Lock** (`hard_locked_at`) = the Stage's first Match starting: earliest of actual start (or "now" if seen live) and Scheduled Start, not cancelled Matches. Unlike a Match's Hard Lock it has no 15-minute lead.
  - **The humans' Lock** (`locked_at`) = the Hard Lock, or earlier once every human current Member has submitted (commit `ca56491`; this supersedes ADR-0003's "Pick'em never Locks early"). The last of them to submit gets a 5-minute final edit window (`pickem_edit_windows`, `lock_reveal::FINAL_EDIT_WINDOW`): during it only its owner can write, and the Lock is its end, capped by the Hard Lock. If a membership change (a kick, a leave) completes the set while no window is open, it Locks at once. A League with no human Member has no early Lock.
  - Everyone's Pick'ems are hidden until `locked_at`. Bot Users are not waited for and are bound by the Hard Lock only: see "Bot Users".
- **Scoring** (only for a Stage whose Pick'em has Locked: a result can arrive earlier, e.g. a forfeit before the planned start, and Points would leak Picks): 1 Point per correct Pick among *settled* teams (3 wins or 3 losses in finished, non-Void Matches of the Stage): `three_nil` needs exactly 3-0, `zero_three` exactly 0-3, `advance` 3 wins with at least one loss. Pick'em Points are separate from Match Points.
- **API** (`api/pickem.rs`): `GET|PUT /api/leagues/{id}/stages/{ordinal}/pickem`. GET → `{stage, teams, lock {locks_at, locked_at, locked, can_edit, edit_window}, my_pickem|null, submitted, eligible, pickems|null}`. `lock` is the viewer's own: `can_edit` is false for everyone but the owner during the final edit window (`edit_window: true`), and in an archived League. `eligible` counts the current Members who joined by the Lock that binds them (Bot Users included), `submitted` those of them with a Pick'em. `pickems` is `null` until Lock, then those Members' Pick'ems: `[{user_id, nickname, avatar_url, is_bot, preliminary, shape, …, points}]`. PUT body `{three_nil[2], zero_three[2], advance[6]}`; errors 404 `not_found` (non-Member, or a Stage without Pick'em: anything but a Swiss Stage today), 409 `pickem_locked`, 422 `pickem_wrong_count` / `pickem_duplicate_team` / `pickem_team_not_in_stage`. JSON carries `shape: "swiss"`; **#15 returns `shape: "playoffs"` from the same endpoints for the Playoffs Stage** (`pickem_stage` in `api/pickem.rs` is the gate to widen). The Pick'em Leaderboard is `GET /api/leagues/{id}/pickem-leaderboard` → `{entries: [{place, user_id, nickname, avatar_url, points}]}`, served from `api/pickem.rs` (not `leaderboard.rs`); **#15 adds its Stage scores to the sum in `leaderboard`**.
- **SPA**: `/leagues/:id/pickem` (`web/src/pages/pickem/`, namespace `pickem`): leaderboard plus one `PickemStage` per Swiss Stage (form until Lock, everyone's Pick'ems after; `StageStatus.tsx` shows "N of M submitted" and the final edit window). #15 adds a bracket component for Playoffs Stages next to it.
- Tests: `tests/api_pickem.rs` (setup has a Swiss Stage of 16 teams and a Playoffs Stage), `tests/api_bot_pickem.rs` (Bot Users, both shapes), unit tests of the Lock policy in `domain/pickem.rs`.

### Playoffs Pick'em (ticket #15)

- **Same endpoints, second shape.** `GET|PUT /api/leagues/{id}/stages/{ordinal}/pickem` serve a Playoffs Stage too (`pickem_stage` accepts Swiss and Playoffs; a Groups Stage still answers 404, so an Event without a Swiss Stage offers only the Playoffs Pick'em). Saved Pick'ems are `{shape: "playoffs", picks: [{rounds_before_final, slot, team_id}], updated_at}`; `PickemJson` is an enum tagged by `shape`. The GET also carries `bracket: {ready, slots: [{rounds_before_final, slot, team_a, team_b, leaf, winner}]}`; `teams` is the first-round teams. PUT takes `{picks: [...]}` (a body of the wrong shape for the Stage is 422 `pickem_wrong_count`). New code: 422 `pickem_bracket_not_ready`.
- **Bracket shape** (`domain::pickem::Bracket::of`) comes from the Stage's Matches' `Playoffs` placements: the deepest `rounds_before_final` R with a placed Match gives `2^R` first slots, and the tree runs from the final (0,0) down to there, so 4 teams = semis + final (3 slots), 8 = 7, 16 = 15. Winners of slots `2n`, `2n+1` meet in slot `n`. A slot with no Match in the data is still a slot with unknown teams. A shallower slot whose two feeders have no Match is also a first slot (a bye). Placements outside the tree (round > 7, slot out of range) and `Unplaced` Matches are ignored.
- **Picks storage**: kind `bracket`, `slot` = heap index `2^rounds_before_final + slot` (final 1, semis 2-3, quarterfinals 4-7), see `slot_id`.
- **Validation** (`BracketPickem::validate`): every slot exactly once (else `pickem_wrong_count`), each winner a participant of its slot: a first slot's two teams, otherwise the winners picked in its two feeder slots (else `pickem_team_not_in_stage`). A team may win several slots, so there is no duplicate rule.
- **TBD first-round teams**: while any first slot lacks a team the bracket is `ready: false`, PUT answers `pickem_bracket_not_ready` and the SPA shows a notice instead of the form. Lock is unaffected: the Hard Lock is still the Stage's first Match start, and `league_matches::evaluate` stamps it for Playoffs Stages too. Teams are always read from the effective view, so a later poll that fills the slots opens the form (if not yet Locked).
- **Scoring** (`score_bracket`): 1 Point per slot whose picked winner equals the winner of that slot's finished, non-Void Match. It is in the same sum as the Swiss Stages in `GET .../pickem-leaderboard` and in each revealed Member's `points`.
- **Archive**: the PUT handler (`api/pickem.rs::save`) calls `require_writable(&league)` right after `require_member`, before either shape is validated, so both are read-only in an archived League.
- **SPA**: `pages/pickem/bracket.ts` is the pure logic (`setWinner` propagates a pick into the next round and clears dependent picks, `participants`, `isComplete`, `toPicks`/`fromPicks`), tested by `web/scripts/bracket.test.mjs` (`npm test`). `PlayoffsStage.tsx` renders it (form until Lock, everyone's read-only brackets after, with ✓/✗ once a slot is decided). `PickemPage` picks `PlayoffsStage` or `PickemStage` by Stage kind.
- Tests: `tests/api_pickem_playoffs.rs` (8-team bracket as the only Stage; 4, 16 teams; TBD first round; Event without a Swiss Stage). `tests/api_pickem.rs` no longer expects the Playoffs Stage to be 404.

## Scoring and Leaderboard (ticket #7)

- **Points are never stored.** The Leaderboard is computed on every read from `LeagueMatches` (the effective Match view + the League's Predictions), so a result from a poll, and #13's Overrides, are reflected at once with no recalculation step. Consequently `poller::after_poll` has no scoring hook; do not add one.
- **Pure policy** in `domain/scoring.rs`: `judge(&Match, Option<TeamId>) -> Verdict` (`Correct | Wrong | Missing | Void | Pending`; a Void Match is `Void` whatever was predicted), and `leaderboard(members, &[ScoredMatch { game, playoffs }], pick_of) -> Vec<LeaderboardRow>` with shared places (1, 1, 3). `LeaderboardRow { place, user_id, points, playoff_points, correct, wrong }` and `percent_correct()` (correct / (correct + wrong), rounded; Void, Pending and Missing are not in the denominator; `None` before any).
- **Reuse**: `api::leaderboard::ranking(&LeagueMatches, &[UserId]) -> Vec<LeaderboardRow>` ranks the League's Members over every Match. #16 "Points gained today": call `scoring::leaderboard` with only that day's Matches (it is the same function over a subset) and read `points`; the current place comes from `ranking`. #17 medals: map `LeaderboardRow::place` 1/2/3 to 🥇🥈🥉, shared places share the medal. Only pass current Members (`store::leagues::members`), so Members who left or were kicked drop off; late joiners simply have `Missing` for earlier Matches.
- Playoffs Matches are those whose Stage `kind` is `playoffs`.
- **API**: `GET /api/leagues/{id}/leaderboard` → `{ rows: [{ place, user_id, nickname, avatar_url, points, playoff_points, percent_correct|null }] }`, ordered by place then nickname. `MatchCard` gained `my_result` (`pending|correct|wrong|missing|void`) and `my_points`. `GET /api/leagues` items gained `my_place` (null if not ranked) and `my_points`.
- **SPA**: `/leagues/:id/leaderboard` (`web/src/pages/leaderboard/`, namespace `leaderboard`, place 1 gold, my row highlighted). #17 should render medals in this page. #14's Pick'em Leaderboard is separate.

## Archive (ticket #17)

- **The final** is the Playoffs Match with `rounds_before_final == 0`, finished with a winner, read from the League's *effective* Match view (`domain::league::final_decided`). A Void final (cancelled, or finished with no winner) does not archive. So when #13 sets a winner by Override in one League, only that League archives.
- **Archiving** is `leagues.archived_at`, set once by `store::leagues::archive` (`WHERE archived_at IS NULL`, never cleared, even if the final's data later changes). `poller::after_poll` calls `poller::archive_if_final_decided(state, league, matches, now)`; it is idempotent. **#13: call it right after an Override sets a winner** (with a freshly evaluated `LeagueMatches`) so the League archives at once instead of on the next tick. The poller already skips Events with only archived Leagues, and Locks need no more evaluation.
- **Read-only guard**: `api::leagues::require_writable(&league)` returns 409 `league_archived`. Call it right after `require_member`/`require_admin` (before reading the body or validating) in **every write that changes the game**. Applied today to: Prediction PUT, Pick'em PUT, join via Invite Link, kick, and every Override endpoint (#13; test `archived_leagues_reject_overrides` in `tests/api_overrides.rs`).
- **Still allowed after archiving**: leaving, deleting (creator), reissuing the Invite Link and changing roles (none of them changes a score). Joining and kicking are rejected so the final Leaderboard keeps its Members; leaving does remove the leaver from the Leaderboard, which is accepted.
- **Medals**: `web/src/components/Medal.tsx` renders 🥇🥈🥉 for places 1-3; shared places share a medal because places are already numbered 1, 1, 3. `LeaderboardPage` and `PickemPage` show it only when `GET /api/leagues/{id}` has `archived_at` set. The League page shows an archived banner and hides the Invite Link and Kick controls.
- Tests: `tests/api_archive.rs`.

## Overrides (ticket #13)

- **Where they apply**: `domain::effective_match::effective_view(base, &LeagueOverrides)` is the only place. `league_matches::effective_view_and_overrides` loads the inputs (`store::overrides::for_league`: the League's hand-added Matches + the Overrides in force) and `league_matches::evaluate` uses it, so Lock/Reveal, scoring, Pick'em, notifications and archive all follow Overrides with no extra step. `LeagueMatches.overrides` carries them for display. `league_matches::admin_view` is the same view **with** hidden Matches (what admins work on). `league_matches::effective_view` keeps its old signature.
- **Fields** (`domain::effective_match::Field`, re-exported as `store::overrides::Field`; `MatchOverrides::fields()` returns them): `scheduled_start` (replaces the Scheduled Start), `result` (winner → Finished with that winner; `winner` NULL → Void, i.e. Cancelled; the score is dropped unless it agrees), `teams` (team A / team B, chosen from the Event's teams: the League-scoped "fix a team mapping"; a source winner keeps its side), `hidden`, (in the effective view a winner is always one of the Match's two teams: a `result` Override whose winner no longer plays is not applied, and a stored winner who does not play makes the result absent, Finished turning Live), and `added` (history record of a hand-added Match).
- **Storage** (`migrations/1300_overrides.sql`): table `overrides` is an **append-only history** (`league_id` cascade, `match_id` without FK, value columns `scheduled_start`/`winner`/`team_a`/`team_b`, `cleared`, `author_id`, `created_at`). The Override in force for (match, field) is the latest row unless it has `cleared = 1` (`store::overrides::in_force`). A newer Override replaces an older one; removing writes a `cleared` row. Nothing is ever deleted, so the history keeps everything.
- **Hand-added Matches** are `matches` rows with a local negative id (`allocate_local_ids`) and the new column `matches.league_id` (cascade from `leagues`). `store::events::base_view` leaves them out (`league_id IS NULL`), so other Leagues, the poller's cadence and the fallback chain never see them: they are never linked to a fallback record nor adopted by HLTV. If the Data Sources later list the same Match, the League has both and an admin hides one. Their `source` column is `'manual'`; `MatchCard.source` is `null` for them.
- **Decisions**: an Override wins over every Data Source update until it is removed. ADR-0003 holds: a Scheduled Start Override moves a Lock that has not happened; stored Lock/Reveal stamps are never cleared (a hidden Match keeps its stamps and comes back with them). **Predictions after a teams Override**: a Prediction counts only while its team plays the Match in the effective view (filtered once in `league_matches::evaluate`); otherwise it is as good as none (no Reveal count, `missing` in scoring, not shown). The row is kept, so removing the Override restores it; while the Match is open the Member can predict again. A Match that already Revealed stays Locked.
- **API** (`api/overrides.rs`): `GET /api/leagues/{id}/overrides` (Members) → `{entries (newest first: id, match_id, match, field, cleared, scheduled_start, winner, void, team_a, team_b, author {user_id, nickname}, created_at), teams, stages, hidden}`; `POST /api/leagues/{id}/matches/{match_id}/overrides` (admins) body `{"field": "scheduled_start"|"result"|"teams"|"hidden", ...}` → 201 entry; `DELETE .../overrides/{field}` (admins) → 200 the `cleared` entry, 404 if not in force; `POST /api/leagues/{id}/matches` (admins) `{stage, team_a, team_b, scheduled_start, format?, placement?}` → 201 `{id}`; `GET /api/leagues/{id}/data-warnings` (admins only, 403 otherwise) → `{conflicts, unmatched}` of the Event, read-only. Every write calls `require_admin` then `require_writable`, evaluates the League at once and calls `poller::archive_if_final_decided`. Errors: `team_not_in_match`, `team_not_in_event`, `same_team`, `stage_not_found`, `override_invalid` (422). Nothing here calls `external_ids::set_manual` (it would change every League on the Event).
- `MatchCard` gained `overridden` (fields in force) and `added_by_hand`; `source` is now nullable.
- **Re-keying** (`rekey_match` / `rekey_team`) moves `overrides.match_id` / `winner` / `team_a` / `team_b`, and the `reminder:`/`reveal:` keys in `notification_log`, so a Reveal announced under a local id is not announced again after HLTV adopts the Match.
- **SPA**: `/leagues/:id/overrides` (`web/src/pages/overrides/`, namespace `overrides`): history for everyone; for admins of a non-archived League a "Correct a Match" form, the Overrides in force with Remove / Show again, "Add a Match by hand" and the warnings. Match cards show "Override: …" and "Added by a League Admin" (`matches` namespace).
- Tests: `tests/api_overrides.rs` (scoping, Lock and ADR-0003, source updates vs Overrides and removal, result/Void recalculation, archive at once, archived Leagues reject Overrides, admin-only, validation, hidden, hand-added, history, teams + Predictions, warnings gate, League deletion), `tests/override_rekey.rs` (Overrides follow a re-key, Reveal not announced twice, warnings with real conflict/unmatched data from a fallback chain).

## Notifications (ticket #16)

- **Entry point**: `notifications::after_poll(state, league, matches, now)`, the one call #16 makes inside `poller::after_poll`. **Put it before #17's archive call**: a League archived at the final stops being passed to `after_poll`, and the final's match day digest must go out in the same pass that archives (an archived League sends nothing further; the function also returns at once for `archived_at.is_some()`).
- **Layers**: `notifications/due.rs` decides what is due, pure, from `LeagueMatches` (the effective view; Overrides apply once #13 feeds them in). `notifications/messages.rs` holds every text, in en/ru/uk, in one catalog (`key -> template with {placeholders}`, no plural forms: a number follows a label). `notifications/mod.rs` does dedupe, preferences, rendering in the User's language and the send. Adding a message: a key constant and a template in all three catalogs; unit tests fail if the languages differ in keys or placeholders. Texts are plain (no Telegram parse mode), so names need no escaping.
- **Dedupe**: table `notification_log (key PK, league_id, user_id, sent_at)`, cascading from leagues and users, so League deletion keeps working. Keys: `reminder:<league>:<match>:<user>`, `reveal:<league>:<match>:<user>`, `digest:<league>:<UTC date>:<user>`. Everything is per League, so a Member of two Leagues on one Event gets a message per League, with the League's name in it.
- **Port change**: `Notifier::send` returns `Result<Delivery, NotifyError>`. `Delivery::Sent`, or `Delivery::Undeliverable` (the User never started the bot or blocked it, Telegram does not know the chat, or no bot is configured): not an error, and the log entry **is written**, so the poller does not retry forever. `NotifyError` is a passing failure (network, 429, 5xx, bad token): **no** log entry, the next 20-second pass tries again, and that is bounded because each type has a time window (below). A turned-off type writes no entry either.
- **Production adapter**: `ports/telegram.rs` `TelegramNotifier` (reqwest + rustls): `POST https://api.telegram.org/bot<BOT_TOKEN>/sendMessage {chat_id, text}`; 403 and 400 "chat not found" are `Undeliverable`; no `BOT_TOKEN` sends nothing. The token is never logged (errors drop the URL). Tested against a local listener (`tests/telegram_notifier.rs`); never against Telegram itself. Dev-login Users have negative Telegram ids, so the real bot answers "chat not found" for them.
- **Preferences**: columns `users.notify_reminder|reveal|digest` (default on). `GET /api/me` has `notifications: {reminder, reveal, digest}`; `PATCH /api/me` takes the same object, partial (`{"notifications": {"digest": false}}`). SPA: three checkboxes on the profile page (`account` namespace).
- **Reminder**: for each Match that is Upcoming, not Locked, with both teams known, from Lock minus 30 min (`REMINDER_LEAD`; Lock is the League's effective one from the Lock/Reveal policy) until Lock, to every Eligible Member without a Prediction. A Match the poller first sees inside the window still gets a **late reminder** (the text says the real minutes left): a late reminder beats none while the Match is open. The key has no Lock time, so a postponed Match does not remind the same Member twice.
- **Reveal**: announced for every Match whose stored `revealed_at` is at most 3 h old (`REVEAL_ANNOUNCE_WINDOW`), which is what stops a burst of old Reveals when the feature first runs on existing data (or after long downtime). Recipients are the Eligible Members (`outcome.eligible`), so a Member who joined after the Lock, or left, is not told, and a Member who did not predict is. Skipped: Void or cancelled Matches, and Matches nobody predicted. The text carries the split of the Eligible Members' picks ("NAVI 2 : 1 FaZe"), which is already public after Reveal.
- **Match day**: the UTC date of a Match's start, where start is the earlier of its actual start and its current Scheduled Start (so a postponed Match moves to its new day, an early start counts early, and a Match the poller saw late, whose actual start was stamped "now", stays on its scheduled day). KallBet stores no User time zone, so one fixed zone keeps the rule stable. **Daily digest** for a day: sent once all its Matches are done (Finished or Cancelled; a Match whose start is over 12 h ago without a result counts as done, `STALE_AFTER_START`), at least one scored (Finished, non-Void) Match, and now is within 6 h after the day's end (`DIGEST_GRACE`, so history is not announced). Recipients: current Members who joined before the day ended. Text: Points gained over that day's Matches (`scoring::leaderboard` over the day's Matches), the current place and total from `api::leaderboard::ranking` at that moment.
- Tests: `tests/api_notifications.rs` (Seam 1, with the fake clock and `RecordingNotifier`), unit tests in `notifications/messages.rs`, `tests/telegram_notifier.rs`. `RecordingNotifier::make_unreachable(user)` makes a User answer `Undeliverable`; `undeliverable()` lists those attempts; `fail_with` makes sends a passing failure.

## Bot Users (ticket #22, spec #21) — read before #23 and the sidecar tickets

A Bot User is a `users` row with `is_bot = 1` (`User::is_bot`, in every User JSON). ADR-0003 and ADR-0004 each carry an amendment for them; `GLOSSARY.md` defines Bot User and Hard Lock.

**Auth (`api/bot_auth.rs`, `auth/bot.rs`, `store/bots.rs`).**

- `POST /api/auth/bot`, header `Authorization: Bearer <KALLBET_BOT_SECRET>`, body `{"bot_key", "nickname", "avatar_url"?, "language"?}` → 200 `{"user": User, "token": "<64 hex>"}`. Errors: 503 `bot_auth_unavailable` (secret unset), 401 `unauthorized` (missing or wrong secret; checked before the body is parsed), 400 `invalid_body`, 422 `bot_key_invalid` (1-64 printable ASCII characters, no spaces), `nickname_invalid` (the usual 3-20 rule), `language_invalid`, `avatar_url_invalid` (http(s), at most 512 characters). These codes have no SPA texts: no human sees them.
- **Idempotent by `bot_key`.** A known key returns the same Bot User with its profile set to the body: Nickname, avatar (left out or `null` = no avatar) and language (left out = unchanged; English for a new bot). A new Bot User starts with every notification switch off and a negative `telegram_id` below every existing one. A Nickname another User holds becomes the first free `Name2`, `Name3`, ...; a variant the bot already holds counts as free, so repeated calls do not drift.
- **One token per bot key, rotated on every call** (`bot_tokens`: `token_hash` SHA-256 hex, `user_id`, `bot_key` UNIQUE, `created_at`). Each call returns a fresh random token and the previous one stops working at once; tokens do not expire otherwise. So a sidecar registers each bot on its first tick, keeps the token in memory, and registers again when a request answers 401 (`Sidecar::tick_bot`; the HTTP adapter turns a 401 into `PlatformError::Unauthorized`, and the tick then runs once more with the new token). Two processes sharing a bot key revoke each other's token on every registration.
- **`CurrentUser`** (`auth/session.rs`): a session cookie, when present, decides alone; a request without one is looked up by `Authorization: Bearer` in `bot_tokens`. Every handler that takes `CurrentUser` therefore accepts a Bot User, with the same membership and role gates (join by Invite Link, kick, 404 for non-Members). Branch on `user.is_bot` only where a rule differs. The shared secret is not a User.
- **Notifications**: `notifications::deliver` skips a Bot User whatever its switches say (no send, no log entry). `notifications::due` still lists Bot Users as recipients; do not rely on it to filter.

**Lock and Reveal (`domain/lock_reveal.rs`).**

- `match_locks` has a third stamp, `hard_locked_at` (`Stamps::hard_locked_at`, `Transition::HardLocked`): the Lock the schedule or the Match brings (Scheduled Start − 15 min, actual start, cancellation), stored once and never cleared like the others. `locked_at` is now the **humans'** Lock: an early Reveal or the Hard Lock, whichever came first. Migration `2200_bot_users.sql` set `hard_locked_at = locked_at` for every Lock stored before Bot Users existed.
- `MemberSpan` has `is_bot` (`store::leagues::member_spans` loads the spans with it). The early Reveal waits for the human Eligible Members only (`Outcome::awaited`); with none of them (a League of Bot Users only) there is no early Reveal. `Outcome::eligible` holds humans and Bot Users: a human is Eligible if they joined by `locked_at`, a Bot User if it joined by `hard_locked_at`, so a Bot User that joins after the humans' early Reveal still counts. `Outcome::is_locked()` is the humans' question, `is_hard_locked()` the Bot Users'; `hard_lock_time` is a Bot User's countdown.
- **Prediction endpoint** (`api/predictions.rs`): `user.is_bot` takes `predict_as_bot`: rejected only by `require_writable` (409 `league_archived`) and by the Hard Lock (409 `match_locked`), written by `store::predictions::upsert_for_bot` (conditional on no stored Hard Lock, same transaction pattern as `upsert`). It never opens the final edit window and is not blocked by a human's window. The window goes to the last *human* (`outcome.awaited`).
- **Matches view** (`api/matches.rs::view_for(matches, &User)`), for a Bot User viewer: `lock` describes the Hard Lock (`locks_at` = Hard Lock time, `locked`/`locked_at`/`can_predict` by it, `edit_window: false`), and before Hard Lock `predictions.revealed` **and** `predictions.revealed_at` are `null` even after the humans' early Reveal. This is what keeps ADR-0003's point: a Bot User can still change its pick, so it sees nobody's. **#23: the Rationale goes through the same `predictions_view`; keep it behind the same `blind` check, and do not add another endpoint that returns Predictions without it.** For human viewers each revealed Prediction gained `is_bot` and `preliminary` (`is_bot` and not yet Hard Locked).
- `predictions.count` / `eligible` ("N of M predicted") count Bot Users too (decision: they are Eligible Members; the spec leaves the numbers as they were). So humans can see "2 of 3 predicted" and then the Reveal, when the one missing is a Bot User.

**Pick'em (`domain/pickem.rs`, `store/pickems.rs`, `api/pickem.rs`) — read before #28.** The same exception in the same shape, per Stage; how the Lock works for humans is in "Pick'em".

- `pickem_locks` has a second stamp, `hard_locked_at` (`pickem::Stamps`): the Stage's first Match starting, with **no 15-minute lead** (so a Stage's Pick'em Hard Locks 15 minutes *after* the Hard Lock of its first Match). `locked_at` is the **humans'** Lock: their early Lock or the Hard Lock, whichever came first. Both are stored once and never cleared; a postponement before the Hard Lock moves it, one after it does not.
- **Migration `2201_pickem_hard_lock.sql` does not backfill** (decision; unlike `2200`, which set `match_locks.hard_locked_at = locked_at`). A Pick'em Lock stored before the deploy keeps `hard_locked_at` NULL, and the first evaluation after it (a poller tick, or the Bot User's own GET or PUT, which evaluate in the same transaction before they check) stamps the Hard Lock for every Stage whose first Match has started by the data. So a played Stage stays closed, and a Stage the humans had already Locked early stays open to the Bot Users that join later, until it starts; a backfill would have closed exactly those. Accepted edge case: an old Lock that was stamped because a Scheduled Start arrived, after which every Match of the Stage was postponed with none started, is open to a Bot User until the new start. No Bot User existed before the deploy, so none saw a Pick'em of such a Stage, and it stays blind until then. The humans' Lock is untouched in every case.
- **Quorum**: the early Lock waits for the human current Members only (`StageState::awaited`), so a Bot User that has not submitted holds nobody up, and a League of Bot Users only has no early Lock. A Bot User's submission never opens the final edit window (`is_final_submission` is false for it), which goes to the last *human*.
- **When a Bot User may submit and refresh**: `PUT /api/leagues/{id}/stages/{ordinal}/pickem` with the usual body creates or replaces its own Pick'em as often as it likes, from the moment the Stage's teams are known (Swiss: round 1 is in the data; Playoffs: `bracket.ready`) until the Hard Lock, whatever the humans' early Lock and edit window say (`store::pickems::save_for_bot`, conditional on no stored Hard Lock, same transaction pattern as `save`). A Bot User that joins after the humans' early Lock may still submit and its Pick'em counts; one that joins after the Hard Lock is Locked out.
- **What it gets after the cut-off**: 409 `pickem_locked` from the Hard Lock on, exactly what a human gets, and 409 `league_archived` in an archived League (checked first). Validation errors (422 `pickem_wrong_count`, `pickem_duplicate_team`, `pickem_team_not_in_stage`, `pickem_bracket_not_ready`) and 404 are the same as for a human.
- **What it sees** (`GET` of the same path, as a Bot User): `lock` describes the Hard Lock (`locks_at` = the expected Hard Lock, which is the Stage's earliest Scheduled Start and moves with a postponement; `locked`/`locked_at`/`can_edit` by it; `edit_window: false`), so the humans' early Lock is not visible in it. `my_pickem` is its own. `pickems` is **`null` until the Hard Lock** (or the League's archive), even after the humans' early Lock has revealed everyone's to the humans: `blind` in `api/pickem.rs`. `submitted`/`eligible` are counts and do show. `GET /api/leagues/{id}/pickem-leaderboard` as a Bot User leaves out every Stage that has not Hard Locked (everyone has 0 Points for it), because a result can arrive before the Stage starts and Points would tell it what the others picked. **Do not add an endpoint that returns Pick'ems or per-Stage Pick'em Points without that `blind` check.**
- **What humans see**: from their Lock on, `pickems` holds the Bot Users' Pick'ems too, each with `is_bot` and `preliminary` (`is_bot` and not yet Hard Locked, in a League that is not archived). `submitted`/`eligible` count Bot Users, as "N of M predicted" does. The SPA does not draw `is_bot`/`preliminary` on the Pick'em page yet.
- **For the refresh in #28**: read `lock.locks_at` and `lock.can_edit` from the GET as the Bot User; refresh before `locks_at`, and treat a 409 `pickem_locked` as final for that Stage. `my_pickem.updated_at` tells when it last wrote.

**SPA**: `MatchCard.tsx` draws a Bot User's revealed pick as a pill with a "Bot" badge (dashed, with an asterisk, while `preliminary`) and shows a hint line while any revealed pick is preliminary. The pure part is `pickMark` / `hasPreliminaryPick` in `layout.ts` (tests in `web/scripts/matches-layout.test.mjs`); strings are `matches:bot.*`.

**Tests**: `tests/api_bot_auth.rs` (secret gate, registration, idempotency, token rotation, Nickname collisions, validation), `tests/api_bot_users.rs` (membership, human quorum, bot-only League, the pre-Hard-Lock exception at T-22/T-15, early start, cancellation, postponement, archive, non-leakage, `is_bot`/`preliminary`, notifications, Bearer on other endpoints), `tests/api_prediction_ownership.rs` (Bearer path), `tests/lock_atomicity.rs` (a Hard Lock stamped between check and write), unit tests in `domain/lock_reveal.rs`. Pick'em: `tests/api_bot_pickem.rs` (each rule for a Swiss Stage and a Playoffs bracket: human quorum, bot-only League, the edit window, writes until the Hard Lock, late joiners, early start, postponement before and after, archive, non-leakage in the GET and the Leaderboard, `is_bot`/`preliminary`, a Hard Lock stamped between check and write), unit tests in `domain/pickem.rs`.

## Prediction Rationale (ticket #23, spec #21) — read before the sidecar's submission code

A Prediction may carry a **Rationale** (`GLOSSARY.md`). It rides on the Prediction everywhere, so it follows every rule of #6 and #22 without a rule of its own.

- **Storage**: `predictions.rationale_json` (`migrations/2300_prediction_rationale.sql`), JSON of `domain::rationale::Rationale`. Because it lives on the Prediction's row, re-keying (`rekey_match`/`rekey_team` move the row), team Overrides (`league_matches::evaluate` drops the whole Prediction while its team does not play) and League deletion (cascade) need nothing extra. It names no team: `p_win` is the picked team's probability. `store::predictions::{upsert, upsert_for_bot}` take `Option<&Rationale>` and write it with the pick in the same conditional statement; `Prediction.rationale` is `#[serde(skip)]`.
- **Write**: `PUT /api/leagues/{id}/matches/{match_id}/prediction` `{team_id, rationale?: {p_win, override_market?, preliminary?, summary: {en?, ru?, uk?}, factors?: [{kind, evidence_url}]} | null}`. The Prediction is replaced as a whole: a write without `rationale` (or `null`) leaves it without one, so the sidecar must resend the Rationale on every update. Humans may send one too (the SPA never does). Validation (`Rationale::parse`, after membership and `require_writable`, before the Lock checks): `0 <= p_win <= 1`; `summary` has at least one of `en`/`ru`/`uk`, each non-blank and at most 1000 characters; at most 8 factors; `kind` from the closed list `stand_in`, `roster_change_30d`, `igl_or_coach_change`, `visa_or_travel`, `illness_or_emergency`, `technical_or_dq`; `evidence_url` an absolute http(s) URL with a host, at most 512 bytes, no whitespace; unknown fields are refused. Every failure, including wrong JSON types, is 422 `rationale_invalid`. The two booleans default to `false`, `factors` to `[]`. The response does not include the Rationale.
- **Read**: only `api::matches::predictions_view`, as `RevealedPrediction.rationale` (`null` when none). `predictions.revealed` is `null` before Reveal and, for a Bot User viewer, before Hard Lock (#22's `blind`), so the Rationale is too. Do not return it from anywhere else (not in `my_prediction`, not in the PUT response).
- **Two "preliminary" flags**: `RevealedPrediction.preliminary` is the server's (a Bot User's pick before Hard Lock, may change); `rationale.preliminary` is the author's own "early draft" flag. The SPA shows both, differently.
- **SPA**: `pages/matches/RationalePanel.tsx` renders, under the teams of a revealed card, one collapsed `<details>` per pick with a Rationale (Bot Users first): win percentage of the picked team, an "against the market" badge for `override_market`, "may still change" while preliminary, then the summary in the interface language, factor pills linking out (`target="_blank" rel="noopener noreferrer"`, http(s) only) and the draft note. Pure logic in `pages/matches/rationale.ts` (`summaryFor`: the viewer's language, else English, Russian, Ukrainian, flagged as a fallback; `winPercent`; `externalLink`; `factorLabelKey`; `rationalePicks`), tested by `web/scripts/rationale.test.mjs`. Strings: `matches:rationale.*`, `matches:errors.rationale_invalid`.
- **Tests**: `tests/api_rationale.rs` (hidden before Reveal, shown after, blind Bot Users until Hard Lock, update at T-22 and refusal at T-15, a write without one clears it, bounds, every malformed case, teams Override, League deletion, re-key of a local Match), unit tests in `domain/rationale.rs`.

## AI Sidecar (ticket #24, spec #21)

The Cargo workspace runs both packages with `cargo test`. The server stays at the root. The standalone binary and library in `sidecar/` are named `kallbet-ai`. `config.rs` accepts multiple profiles with distinct keys, optional avatar URL and language. `registry.rs` composes the ports. The binary calls `Sidecar::tick()` every minute (`SIDECAR_TICK_SECONDS`; see "Production wiring"). Each tick reads the injected clock once, uses each bot's kept token (registering it on the first tick and again after a 401), joins its Invite Links, polls its active Leagues, runs the Pick'em step, then evaluates writable Matches with two known teams. A missing pick triggers Draft. In [T−25m, T−15m) (`PRE_LOCK_LEAD`, `HARD_LOCK_LEAD` in `model.rs`; `hard_lock(start)` is the one place the 15-minute lead is applied, by the scheduler, the odds chain, the Pick'em step and the backtest cutoff alike) the bot uses PreLock, including when it first sees a Match in that window. KallBet enforces early starts, cancellations, membership and Hard Lock on the write.

**Failures stay local** (`Sidecar::on_failure`, `OnFailure::Isolate` in production). A failure of one Invite Link, one League's Match list, one Stage's Pick'em (`PickemStep::tick` returns a `StageFailure` per failed Stage and goes on) or one Match is logged at `error` and appended to `tick_failures` (migration `2401_tick_failures.sql`; read with `audit.failures()`), and the tick goes on with the next one. An Invite Link answering 404 `invite_invalid` or 409 `league_archived` (`LeaguePlatform::join` returns `Join::InviteInvalid` / `Join::LeagueArchived`, also for a link that is not a `/join/<code>` URL) is logged and recorded once per run and skipped until restart; a kicked bot rejoins through a link that still works, as any Member does (`docs/sidecar.md`). Only signing in, listing the bot's Leagues, and any `TemporalLeakError` end the tick (with an error, which the loop counts). **No Prediction is dropped for want of an LLM** (story 32): when the policy wants an adjustment and every chain, or the Arbiter, fails, `DecisionPolicy::decide_unadjusted` decides from the inputs alone (`HybridAnchored`: the anchor, with a Rationale saying in three languages that no LLM adjustment was available) and that Prediction is submitted and recorded in `unadjusted_submissions`, once per run. It is not the run's decision: a later tick with the same dossier asks the LLM again (cheaply while a breaker is open) and, once it answers, decides and submits as usual. `audit.submissions()` lists both kinds in order. The backtest runs `OnFailure::Abort` (the old behaviour: the first failure ends the tick, and an LLM profile without an answer never submits the anchor). Tests: `tests/failures.rs`.

`AsOf::new` checks observation time and `AsOf::at` rechecks when cached data enters a dossier for an earlier cutoff. `vrs.rs` reads Valve's global Markdown standings and selects the latest snapshot strictly before the live cutoff. It dates publications at the last nanosecond of the stated UTC day. Team lookup ignores case. Valve's fixed-RD (75) Glicko expectation supplies the map probability, followed by the Bo1, Bo3 or Bo5 conversion. Missing ratings yield no VrsOnly prediction.

`audit.rs` inserts the SHA-256 dossier hash scoped by bot, League, Match and tier before evaluation. Decisions (including abstentions) and successful submissions are separate append-only records. A failed PUT can reuse the saved decision. The audit file also holds original VRS snapshots and tables for the feed, debate and Pick'em adapters, and, in a backtest's own audit file, `backtest_runs`. Run one live scheduler per audit file and bot identity.

### Pick'em Solver and Stage submission (ticket #28)

The live scheduler registers `adapters::pickem::new` with the clock, odds source and signal estimator. The HTTP adapter reads Stage groups and the bot's own Pick'em view. A Swiss Stage needs 16 teams, and Playoffs needs `bracket.ready`. Published opening Matches use series market probabilities converted to map probabilities. Once a Match reaches its own Hard Lock, the adapter can still read pre-Stage quotes from cached Event batches. Hypothetical pairings and missing prices use dated VRS. Unrated matchups use an even probability, including a ready Stage with no feed coverage.

`MonteCarloPickemSolver::solve` accepts a dated Stage and dated pairwise map probabilities for replay. It rejects observations at or after the cutoff and Stage views with results or later-round participants. Swiss runs 25,000 simulations by default. Use `seeded` for a repeatable stream or `solve_with_rng` to inject outcomes. The simulator uses published opening pairs when available and an explicit seed list when supplied. The live server supplies no initial seeds, so pre-Stage pairwise strength estimates the seed order. Same-record pools use Buchholz and initial seed, avoid rematches, and follow Valve's six-team priority table in rounds four and five. Advancement and elimination series use Bo3. An all-Bo3 opening round selects Bo3 throughout. The assignment maximises expected Points with separate probabilities for 3-0, 0-3 and advancement with a loss. Playoffs propagates unconditional slot win probabilities up the server's bracket tree and maximises total expected Points subject to advancing each picked winner through its feeders. [Valve Major Supplemental Rulebook](https://github.com/ValveSoftware/counter-strike_rules_and_regs/blob/main/major-supplemental-rulebook.md#swiss-bracket)

The initial submission can occur throughout the writable window. In the final 30 minutes a changed input permits one refresh, including when the initial submission also occurred in that window. The input is two hashes, stored as `ratings/rosters` in `submitted_pickems.input_hash`: the Stage with its pairwise ratings (odds or VRS), and the roster facts (`liquipedia_roster`, `vrs_roster_diff`) of every Stage team, which the step asks of the Context Enricher (`pickem::new` takes it) for the teams in pairs (story 42: "if odds or rosters changed"). When the enricher fails the roster hash is `-` and the comparison goes by the ratings alone, so an outage neither triggers nor blocks a refresh on the odds. Tests: `tests/pickem_rosters.rs`. The adapter reads the bot-specific Lock and handles a concurrent Stage Lock on PUT. Successful payloads and input hashes are recorded in `submitted_pickems`. The human early Lock leaves the bot's window open.

`sidecar/tests/pickem_e2e.rs` drives both Stage kinds through the shared Seam 1 harness and checks submissions, refreshes and Points on the server's Pick'em Leaderboard. `sidecar/tests/pickem_solver.rs` covers seeded pairing, scoring, bracket consistency and the pre-Stage cutoff. It reuses the saved Liquipedia responses and Valve standings under `sidecar/tests/fixtures/{context/liquipedia,vrs}`.

### Odds and MarketOnly (ticket #25)

- **Team names** are compared everywhere in the sidecar (odds lines, Liquipedia rosters, Valve standings, news, the backtest archive) by one key, `kallbet_ai::team_names::team_key`: lower-case alphanumerics without filler words (`team`, `esports`, `gaming`, `clan`, `club`, `gg`) and one alias table (`navi` → `natusvincere`, `gosh` → `bcgame`, ...). Add a new short or former name to that table, never to an adapter.
- Set `"policy": "MarketOnly"` in a bot profile. It picks the team with the higher fair series-win probability, choosing team A at 50/50. When the odds chain has no line, it delegates to `VrsOnly`. Both policies skip LLM calls. `DecisionPolicy::wants_adjustment(bot)` defaults to false. Policies that use an LLM opt in per profile.
- `adapters::odds::build(&audit)` installs OddsPapi → Polymarket → Kalshi. `OddsSource` returns the probability for team A. Both team names must agree after normalization, including known aliases. A quote must be within six hours of Scheduled Start. The nearest line wins and an equal-distance tie is treated as ambiguous. Pinnacle decimal prices are inverted and divided by their sum. Polymarket's series moneyline prices and Kalshi's two YES bid/ask midpoints are normalized the same way.
- Use `SIDECAR_ODDSPAPI_TOURNAMENTS={"8302":[400014]}` and `SIDECAR_POLYMARKET_TAGS={"8302":"pgl-major-singapore-2026"}` for PGL Major Singapore 2026. OddsPapi also listed a second, empty entry with the same name (51216). The key comes from `ODDSPAPI_API_KEY`. Missing mappings skip the corresponding source, as does a missing OddsPapi key. The public Kalshi CS2 series runs by default, with `SIDECAR_KALSHI_ENABLED=false` to opt out. [HLTV Event](https://www.hltv.org/events/8302/pgl-major-singapore-2026)
- The sidecar's `odds_batches` table stores timestamped batches, including successful empty results. TTLs are six hours per OddsPapi Event and two minutes per Polymarket Event tag or Kalshi series, except in the PreLock pass: `OddsSource::live_quote` takes the `Tier`, and a PreLock lookup reuses a batch only up to `SIDECAR_ODDS_PRELOCK_MAX_AGE_SECONDS` old (default 600, `OddsConfig::prelock_max_age`), so the final Prediction is made on the closing line ("refresh odds & context" in the spec's schedule). OddsPapi reserves at most 200 batch attempts per UTC month per SQLite file (`ODDSPAPI_MONTHLY_BUDGET`), leaving headroom in its 250-request free tier, and Drafts and the Pick'em step may use only 150 of them (`ODDSPAPI_DRAFT_BUDGET`), so the PreLock refresh keeps 50. A refused reservation is logged and the chain falls through to Polymarket, then Kalshi.
- **OddsPapi budget for one Major** (PGL Major Singapore 2026: three Swiss Stages of 33 Matches and 7 Playoffs Matches, 106 Matches over about 15 match days). PreLock: one batch per Match at most (a batch fetched at T−25 covers its whole window, and every other Match whose window starts within 10 minutes of it shares it), so at most 106. Draft and Pick'em: one batch per six hours at most while Matches are being drafted, and any PreLock batch younger than six hours serves a Draft too: at most 4 a day, about 60 over the Major, under the 150 cap. Total at most about 166 per audit file, under the 200 guard and the plan's 250; a Major spanning two calendar months spreads it over two budgets. Every 429 counts as a request (it is reserved before sending). Two sidecars with the OddsPapi key (a local run beside the VPS one) share the account's 250 but not the guard: run one. Per-source breakers use three consecutive failures or one 429, then a 15-minute cool-down followed by one probe. A successful fetch with no matching line falls through and clears the failure count.
- `OddsSource::live_quote` can advance the injected-clock cutoff after a refresh. The scheduler caps the live evaluation cutoff at Hard Lock and rechecks it before building the dossier. OddsPapi and Polymarket use source timestamps. Kalshi uses response capture time. Every quote must pass `observed_at < cutoff`. The chain's ordinary `quote` method reads only cache batches captured before the supplied cutoff. For replay from saved OddsPapi feeds, `oddspapi::match_settled_fixture` links a Match from the settled Event fixture list and `SettledFixture::quote` selects the last active prices strictly before cutoff and Hard Lock.
- **Raw records** (story 36). The raw record a quote was derived from (the OddsPapi fixture object, the Polymarket market, the Kalshi event, as received) is kept in `raw_feed_snapshots` under `odds:<feed>`, content-addressed (`audit::store_raw`: once per source and content, `observed_at` = first seen), when the quote is made. Whole batches are not kept (they are megabytes; `odds_batches` holds the parsed lines with each record's `raw_hash`); a line quoted from a batch cached before a restart has its hash but its record was kept when first quoted. The context cache follows the same rule: a Liquipedia response (`liquipedia:revision:<page>`) and a feed's XML (`rss:xml:<url>`) are kept once per content, each fetch adding a small marker by hash (`liquipedia:rev:<page>`, `rss:<url>`); Valve snapshots are kept once in `vrs_snapshots` (unique by date and hash). Read them with `audit.raw_records(source)`. Tests: `tests/odds_chain.rs` (`the_raw_fixture_behind_a_quote_is_kept_once_per_content`), `tests/context_enricher.rs` (`an_unchanged_page_or_feed_fetched_again_is_kept_once`).
- `Audit::begin` in `sidecar/src/audit.rs` rounds the market probability to four decimal places when calculating `input_hash`. Adjust `MARKET_HASH_SCALE` there to change the rounding step. The stored dossier, policy, and Rationale keep the original probability. Within one tier, moving inside the same rounding bucket reuses the previous decision.

## LLM Runtimes (ticket #27, spec #21) — read before #29, #30 and #31

Code: `sidecar/src/ports/llm_runtime.rs` (the port) and `sidecar/src/adapters/llm/` (everything else). Paths below are relative to `sidecar/`.

**The port, final shape (#29 may rely on it).** `LlmRuntime::evaluate(bot, dossier, tier, &RolePrompt) -> Result<Option<Value>, LlmError>`. `RolePrompt { role, instructions, schema, attachments: Vec<(label, Value)> }`: attachments are extra labelled JSON inputs (the Arbiter's two briefs). `Ok(Some(v))` means `v` matches `prompt.schema`: every adapter checks it again in Rust (`adapters::llm::schema::valid`, a subset of JSON Schema: `type`, `properties`, `required`, `additionalProperties: false`, `items`, `enum`, `const`, min/max, min/maxItems, min/maxLength; keep role schemas inside it, and inside what the providers accept: every object `additionalProperties: false` with all properties `required`, no numeric bounds). `Ok(None)` only for a bot whose `provider_chain` is empty (the baseline bots). `LlmError`: `QuotaExceeded`, `Transient`, `Timeout`, `Auth`, `InvalidOutput`, `NotConfigured` (unit variants, `Copy`, `PartialEq`). `RolePrompt::adjustment()` is the scheduler's single-agent pass; its schema (`adjustment_schema()`) is strict: `delta` (percentage points for team_a), `factors[{kind (closed enum), evidence_url}]`, `summary{en,ru,uk}`. The decision policy still clamps and validates `delta` and the factors.

**Configuration.** The sidecar config file gains an optional `llm` section (`adapters::llm::LlmConfig`); a bot's `provider_chain` lists provider names in the order they are tried.

```json
"llm": {
  "providers": {
    "claude": {"kind": "claude", "model": "sonnet", "timeout_seconds": 300},
    "codex": {"kind": "codex"},
    "antigravity": {"kind": "antigravity", "model": "gemini-3.8-flash-medium"},
    "proxy": {"kind": "http", "api": "anthropic", "base_url": "http://oauth-proxy:8080/v1",
              "model": "claude-opus-5-5", "api_key_env": "KALLBET_AI_LLM_API_KEY"}
  },
  "web_search_bots": ["oracle"],
  "cooldown_minutes": 30
}
```

CLI providers: `binary` (default `claude` / `codex` / `agy` on PATH; give the full `.exe` path on Windows if it is an npm `.cmd` shim), `model`, `timeout_seconds` (default 300). HTTP providers: `api` `anthropic` (`POST {base_url}/messages`, `x-api-key`, `output_config.format` json_schema) or `openai` (`POST {base_url}/chat/completions`, Bearer, `response_format` json_schema strict), `base_url` up to `/v1`, `model`, `api_key_env` (the *name* of the variable holding the key; leave it out for an OAuth proxy that holds the subscription itself), `timeout_seconds` (180), `max_tokens` (4096). Without `llm`, nothing is configured and only bots with an empty chain work.

**Composition.** `adapters::llm::build(&config.llm, clock)` (called from `registry.rs`) returns `Arc<Providers>`: one `Provider` per configured name, each with **one** circuit breaker shared by every chain that names it. As an `LlmRuntime`, `Providers` runs the calling bot's `provider_chain` as a `FallbackLlm`. `providers.chain(&names)` builds a chain from any list of names: **#29 builds each debate seat's chain this way** (change `debate::build` to take `Arc<Providers>`; `registry.rs` already passes one). `FallbackLlm::answer` also returns which provider answered and how long it took (`Answer { provider, value, elapsed }`) for the `debate_turns` audit; its `evaluate` returns just the value. `Providers::from_runtimes` wraps ready-made runtimes (fakes) with breakers.

- **Failover**: each provider in order; every error moves on to the next. Errors returned: `NotConfigured` when every provider is unconfigured, otherwise the last failure met (a cooling provider contributes the cause that opened its breaker). A name with no provider, a missing binary (spawn `NotFound`), an HTTP provider without `base_url`, with `api_key_env` naming an unset variable, or an endpoint answering 404 is `NotConfigured` and skipped without touching its breaker.
- **Breaker** (`BreakerState`, readable through `providers.breaker(name)`): `QuotaExceeded`, `Transient` and `Timeout` open it for `cooldown_minutes` (default 30); while open the provider is skipped without starting a process. After the cool-down one trial request goes through (half-open; concurrent requests skip it meanwhile): success closes it, another such failure opens it for a new cool-down. A trial that never reports, because its future was dropped (the loop's tick timeout or a shutdown drops the tick), reopens it as a `Timeout` for a new cool-down (a guard in `FallbackLlm::answer`), so the provider is tried again after it instead of staying half-open until restart. `Auth`, `InvalidOutput` and `NotConfigured` do not open it (the provider did answer). The breaker reads the injected `Clock`, so tests set time by hand.

**Leaf adapters.** Each CLI is a pure command builder plus a pure envelope parser (`adapters::llm::{claude, codex, antigravity}::{command, parse}`), run by `CliRuntime` through the `ProcessRunner` port. `TokioRunner` starts the process in a fresh empty temp directory (removed afterwards), writes `Invocation::files` there (codex's schema file), feeds `stdin` and closes it (or gives a null stdin), kills the process when `timeout` passes (`RunError::TimedOut` → `LlmError::Timeout`).

## HybridAnchored and the Debate (ticket #29, spec #21) — read before #30 and #31

Code: `sidecar/src/adapters/debate/` (`policy.rs` the decision policy, `tier.rs` risk flags and the pass rule, `roles.rs` the seats' prompts and the brief schema, `turns.rs` the audit, `mod.rs` the runtime and its config). Paths below are relative to `sidecar/`.

**Using it.** A bot gets `"policy": "HybridAnchored"` and a `provider_chain` of names from `llm.providers`. That alone gives the default behaviour; the optional `debate` section of the config file changes it per bot key:

```json
"bots": [{"bot_key": "oracle", "nickname": "Oracle", "invite_links": ["..."],
          "policy": "HybridAnchored", "provider_chain": ["claude", "codex", "antigravity"]}],
"debate": {"bots": {"oracle": {
  "mode": "tiered",
  "lopsided": 0.80,
  "market_step_pp": 1,
  "fast": ["claude", "codex"],
  "advocate": ["claude", "codex", "antigravity"],
  "devil": ["codex", "antigravity", "claude"],
  "arbiter": ["antigravity", "claude", "codex"]
}}}
```

Every key is optional. `mode`: `tiered` (default), `always` (Draft runs debate too) or `never` (always one agent). `lopsided` (default 0.80, above 0.5, at most 1). `market_step_pp` (default 1, above 0, at most 50): the step, in percentage points, of the market line inside which stored LLM answers are reused, see "Reuse" below. A value outside these ranges fails start-up. `fast` defaults to the bot's `provider_chain`; the seats default to that chain turned by one place per seat, which for `[claude, codex, antigravity]` is exactly the example above: Claude as Market Advocate, Codex as Devil's Advocate, Antigravity as Chief Arbiter, each falling back to the other two. A `HybridAnchored` bot with an empty `provider_chain` and no seats runs with no LLM and submits the anchored pick.

**`HybridAnchored` (`policy.rs`, pure).** `base(&dossier)` is `p_base` for team A: `0.80 · logit(market) + 0.20 · logit(signal.series)` through the sigmoid; with one of the two missing, the other; with neither, `None` and no Prediction. `accept(p_base, &adjustment)` is the whole guardrail on an LLM answer, and `decide` applies nothing else:

- A factor counts when its `kind` is one of the six (`FACTOR_KINDS`) and its `evidence_url` is an absolute http(s) URL in the server's sense (`domain::rationale::is_evidence_url`: so not empty, no whitespace, at most 512 bytes). Others are dropped; duplicates too; at most 8 are kept. That the URL is one the model could really have read is checked one step earlier, by the runtime that sent the dossier: see "Evidence" below. `decide` itself, given an adjustment from some other `LlmRuntime`, checks the form only.
- With at least one factor the shift is clamped to ±8 pp. Without one it is clamped to ±2 pp when `|p_base − 0.5| < 0.03` and to zero otherwise.
- `p_final = p_base + delta/100`, kept inside 1%..99% when shifted. The pick is team A above 0.5, team B below; exactly 0.5 keeps the side `p_base` had (team A when that is even too). `override_market` is true exactly when a market line exists and the pick is not its favourite (team A at an even market, as for `MarketOnly`); the rating alone can cause that, with no LLM involved.
- Rationale: `p_win` of the picked team, the factors that passed, `preliminary` = Draft tier. The summary is the model's (each of `en`/`ru`/`uk` kept when it is non-blank text, cut to 1000 characters), except when the model asked for a shift and all of it was refused: then a fixed text says so, because the model's text would argue for a pick the bot did not make. With no usable summary a fixed text is used too.
- `wants_adjustment` is true, so the scheduler asks `ports.llm` before `decide`.

**`TieredDebateLlm` (`mod.rs`), the sidecar's `ports.llm`.** `debate::build(&config.debate, providers, &audit)` wraps the `Arc<Providers>` of ticket #27 (`registry.rs` does this; #31 passes providers built with `Mode::Backtest`). It implements `LlmRuntime`, so the scheduler is unchanged: it still sends `RolePrompt::adjustment()` and gets an `LlmAdjustment` back. Per run:

1. No anchor (`base` is `None`), or the bot has no provider for the pass: `Ok(None)`, no call.
2. `tier::plan` picks the pass. `tiered`: a Draft run is **Fast**; a PreLock run (the scheduler's T−25..15 window) is a **Debate** unless the Match is a clean mismatch: `p_base ≥ lopsided` or `≤ 1 − lopsided`, no risk flag, and not a Bo1. So a competitive Match, a Bo1 and a flagged Match debate in the window, and nothing debates at Draft unless `mode` is `always`.
3. **Fast**: the scheduler's prompt under the role `predict`, on the `fast` chain: one call.
4. **Debate**: `advocate` and `devil` run concurrently (`tokio::join!`), each on its own `FallbackLlm` chain, each answering `brief_schema()` (`position`, `claims[{claim, kind, evidence_url, favours}]`, `delta`). Then `arbiter` gets the scheduler's prompt and schema with both briefs attached (`"Market Advocate brief"`, `"Devil's Advocate brief"`) and its answer is the run's. A seat whose whole chain fails leaves a `null` brief and the Arbiter still decides; a failed Arbiter fails the run with its `LlmError`.

Every prompt also carries a `"Baseline"` attachment: `{p_base_team_a, risk_flags}`.

**Evidence must be traceable (`policy::Evidence`, pure; applied in `TieredDebateLlm::evaluate`).** Before an answer leaves the runtime, fresh or reused, every factor whose `evidence_url` the run could not have read is removed from it, so the policy sees a factor without evidence: the shift is zeroed (or cut to the ±2 pp tie-break) exactly as for a missing URL, the factor is not in the Rationale, and the model's summary is replaced as for any refused shift. A URL is readable when:

- it is, character for character, a URL of the dossier **as it was sent to the model**: `Evidence::of(&dossier, web)` collects from `dossier.context` every string under a key named `url` or ending in `_url` (a roster fact's `source_url`, a note's `source_url`, a news item's `url`), except `license_url` and `feed_url`, which are in the dossier but are evidence of nothing; or
- the provider that gave the answer ran with live web access (`providers.access_of(provider, bot, tier) == ToolAccess::WhitelistedWeb`: a bot in `llm.web_search_bots`, a PreLock run, `Mode::Live`, **and** a CLI provider: the HTTP adapter sends no tools, so an answer from it never read a page) and the URL is http(s) on `hltv.org`, `liquipedia.net` or a subdomain of either (`WEB_DOMAINS`; a look-alike host or a `user@host` form is not). For a debate that is the Arbiter's provider; for an answer reused from the audit, the provider recorded with it.

The audit keeps the model's answer as given, with every factor it named. A new kind of context fact must name its source under `url` or a `*_url` key to be citable.

**Reuse (`reuse_key` in `mod.rs`).** An LLM answer (the Draft's, each seat's brief, the Arbiter's) is stored and found again under a key coarser than the dossier hash: bot, tier, and a hash of the Match (with its format and start), the rating estimate, every context fact, and of the market only `round(market / market_step_pp)` plus which team it favours. So while the line moves inside one step and keeps its favourite, `evaluate` answers from the audit with no call, the scheduler (whose own `dossier_runs` hash is the precise one) still sees a new dossier, and `HybridAnchored::decide` recomputes the anchor from the fresh line, applies the stored adjustment and runs every guardrail again; the pick and `p_win` follow the market and a new Prediction is submitted. A move to another step, a favourite flip (50.4% to 49.6% is one rounding step but two keys), a new or changed fact, another rating or the other tier is a new evaluation. In `tiered` mode an answered key is not asked again even when the move carries `p_base` across `lopsided` and the planned pass changes; `always` reuses only an Arbiter's answer and `never` only a single agent's.

**Risk flags (`tier::risk_flags`, pure)** read the #26 context facts by `kind`: `liquipedia_roster` with `has_stand_in`, a non-empty `stand_ins` or a coach with `emergency_sub` → `stand_in`; `vrs_roster_diff` with `changed` → `roster_change`; `news_item` whose title or description contains one of `NEWS_WORDS` (stand-in, bench, replace, roster, coach, visa, illness, forfeit, ...) → `news`. A plain result headline raises none. A new kind of context fact raises no flag until it is added there.

**Audit (`turns.rs`, migrations `2900_debate_turns.sql` and `2901_debate_reuse_key.sql`).** One append-only row in `debate_turns` per seat that was asked, also for the Fast pass: `bot`, `match_id`, `tier`, `input_hash` (`Audit::input_hash(&dossier)` of the run that asked, the value `dossier_runs` keys on), `reuse_key` (see "Reuse"), `role` (`predict`, `advocate`, `devil`, `arbiter`), `provider` (who answered; for a failed seat the chain that was tried), `latency_ms`, `status` (`ok` or the error kind, e.g. `quota_exceeded`), `brief` (the seat's JSON, unfiltered). A failover inside a chain is one row, with the provider that answered. Read them with `audit.debate_turns()`. **The log is also the cache**: before a seat is asked, its latest `ok` answer under the same (bot, tier, reuse key) is used, so a bot in two Leagues on the same Match debates once, a retry after a failed Arbiter does not repeat the two briefs, and a reused answer adds no row. A turn that cannot be written to the audit is not used (`Transient`).

**For #31 and #30.** `debate::build`'s signature and `HybridAnchored` are unchanged. Wrap an anonymizer *around* the runtime `debate::build` returns: `evaluate` then receives the anonymized dossier, sends that to the model, and checks evidence against the same placeholders (compared as plain strings, so a placeholder need not look like a URL at that point). What reaches `HybridAnchored::decide` must still be an absolute http(s) URL or the factor is dropped there, so either use URL-shaped placeholders or map them back after the Arbiter. `Providers::from_runtimes` (fakes) reports no web access; `Providers::new` reports what its `Mode` and `web_search_bots` say, for its CLI providers only (`Provider::web`). #30: `market_step_pp` is the only new setting; the sample above shows the defaults.

**Costs to know.** Inside T−25..15 a Match debates once per market step it visits (and per favourite flip or new fact), not once per odds refresh. Each refresh that moved the line by 0.0001 or more still writes a new Prediction with the recomputed `p_win` (the scheduler's precise hash), which costs a PUT and no LLM call.

**Tests.** Unit tests in `policy.rs` (blend against worked numbers, clamp, every malformed factor, tie-break band, `override_market`, summary; evidence: a dossier URL, an invented one, the licence and feed URLs, whitelisted sites with and without web access, look-alike hosts, anonymizer placeholders, and the policy's result after filtering) and `tier.rs` (the pass table, both sides of the threshold). `tests/debate_runtime.rs`: the runtime over three scripted providers with real breakers and a real audit file (one call or three per case, the two advocates started before either answers, the Arbiter's attachments, quota failover inside a seat's chain, configured seats, reuse, retry after a failed Arbiter, a seat with no provider left, risk flags from the saved Liquipedia revision and HLTV feed; ## Retrospective backtest (ticket #31, spec #21)

Code: `sidecar/src/adapters/backtest/`. Paths below are relative to `sidecar/`. The benchmark it produced, and how to rerun it, is in `docs/backtest/`.

**Running it.** `cargo run -p kallbet-ai -- backtest` (from the repository root) reads the archive `tests/fixtures/backtest/` and writes `report.md`, `report.json` and a fresh `audit.sqlite` into `target/backtest/`. Options (`backtest/cli.rs`): `--archive DIR`, `--out DIR`, `--llm FILE` (JSON `{"llm": <the sidecar config's llm section>, "single": [...], "advocate": [...], "devil": [...], "arbiter": [...]}`, provider names; sample `docs/backtest/llm.example.json`), `--answers FILE` (recorded LLM answers: imported before the run, rewritten with every answer after it), `--llm-stage ID` (PandaScore tournament evaluated with real names; default PGL Major Singapore 2026 Stage 1, `22378`), `--blind-stage ID` / `--blind-matches N` (the anonymized slice: the first N Matches of IEM Cologne Major 2026 Stage 1, `20708`, 6), `--blind-direct` (also send the direct Matches through the anonymizer), `--simulations N` (Swiss Monte-Carlo runs, default 25,000). No setting is read from the environment except `SIDECAR_LOG`. Without `--llm` no provider is called: the LLM profiles answer only from `--answers`, and a Match they have no answer for gets no Prediction from them (never the anchor's pick in their name).

**What runs.** The live pipeline, unchanged: one `Sidecar` per profile (`runner.rs`: `vrs` VrsOnly, `market` MarketOnly, `anchor` HybridAnchored with no LLM, `single` HybridAnchored with debate mode `never`, `debate` HybridAnchored with mode `always`), sharing the replay ports, ticked by `Sidecar::tick` at virtual instants:

- `platform.rs`, `ReplayPlatform` (the League Platform port): at each step it shows the Matches whose evaluation instant it is (`Due::Matches`, `can_predict`, no Prediction yet) or one Stage's Pick'em (`Due::Stage`, built from its opening view), and records submissions. The LLM profiles see only the planned Matches (the budget).
- Instants (`ReplayClock`): a Match at `match_cutoff − 1 s`, where `match_cutoff = min(Scheduled Start − 15 min, actual start)` (`backtest::match_cutoff`); the scheduler therefore runs its PreLock pass (Draft if the Match started more than 10 minutes early) and checks every datum against that instant. A Stage's Pick'em at `stage_cutoff − 1 s` (earliest Scheduled Start or actual start of its Matches), by #28's Pick'em step (only in the `vrs` sidecar: every profile would submit the same solver output).
- `feeds.rs`: `ReplaySignal` (all saved Valve snapshots; names compared by `team_names::team_key`, which joins PandaScore names and acronyms, Liquipedia template keys and Valve's names; 2024 headers `2024-11-25` are read too), `ReplayOdds` (OddsPapi via #25's `oddspapi::match_settled_fixture` + `SettledFixture::quote`, then Polymarket's last price, then Kalshi's normalised bid/ask mids, each the last point strictly before the cutoff for a listing of the same teams within 6 h of the Scheduled Start; `quote_from(MarketSource, ..)` asks one source), `ReplayContext` (#26's roster parser on the latest saved Liquipedia Event revision before the cutoff).
- `archive.rs`, `ReplayArchive::load(dir)`: reads plain or `.gz` files and tells their kind by content (see the archive README). Stages come from PandaScore lists; a Stage's opening view from its `lp-<tournament>` revision: Swiss = 16 teams, one `record` group with the Round 1 pairs (format and Scheduled Start from PandaScore), seeds from `tiebreaker=` (2026) or `temp_tie` (2024-2025); Playoffs = the four quarterfinal leaves (`R1M1..4`), semis and a final with its format. A Liquipedia key that matches no PandaScore team leaves the Stage without a view (`opening_problem`, shown in the report).
- LLM: `Providers::new(&llm, Mode::Backtest, clock, runner)`, so no CLI run gets a tool or the web whatever `web_search_bots` says; the breaker cool-down is set to ten years, so a provider that failed with a quota (or timeout, transient) error is never asked again in that run; a seat with a fallback goes on with the rest of its chain, as live, and the report lists the provider under `exhausted`. `debate::build` runs on top, wrapped by `Blind` (below) and `Required` (an LLM profile without an answer fails as `NotConfigured` instead of submitting the anchor). The runner stops the LLM profiles at the first quota or sign-in failure that a chain could not absorb (the run's error, or a failed seat in `debate_turns`); the non-LLM profiles go on.

**Leak guard.** Every replay feed answers only with data observed strictly before the instant it is asked for, and the scheduler re-checks each datum with `AsOf::at(now)`; the Pick'em view is wrapped in `AsOf::new(view, revision_timestamp, stage_cutoff)` by the platform, and #28's solver rejects a view with a winner, a score, a live or finished Match, or a later-round pairing. Any `TemporalLeakError` aborts the run (`Backtest::run` returns it). Real data found one: eight saved Stage revisions had been taken against the actual start, not the earlier Scheduled Start, and were refetched.

**`BlindAnonymizer` (`anonymizer.rs`).** `mask(&dossier)` → masked dossier + mapping: teams `TEAM_ALPHA`/`TEAM_BETA` (other teams `TEAM_03`...), the two active rosters `PLAYER_01..05` and `PLAYER_06..10` (others `PLAYER_11`...), coaches `COACH_nn`, Event title and its path segments `EVENT`, dates `T-<hours>h` before the Scheduled Start, years `YEAR`, month names `MONTH`, revision ids 0, Match and Event ids opaque, Scheduled Start removed, every URL `https://evidence.invalid/<n>` (URL-shaped, so #29's evidence rule holds on the masked dossier). Free text gets the same replacements. A name that only free text mentions (a headline naming a third team or a player) is caught too: `Blind::knowing(archive.known_names())` gives the anonymizer every team (PandaScore) and every team, player and coach of every saved Liquipedia revision, and `mask_knowing` gives a placeholder to each that the dossier's text mentions. A fact whose values still hold a known name or a year afterwards is dropped. A name the archive does not know (a player of a team that is not at the Event) can still pass in free text; the archive has no news, so today free text is roster notes only. `reveal(answer)` maps placeholder URLs and names back; sides are kept, so `delta` and the pick need no mapping (`team(placeholder)` gives the real id). `Blind::new(inner, match_ids)` applies it inside the LLM port: the debate, its reuse key, its audit and its evidence check see the masked dossier, `HybridAnchored::decide` the real one. The Arbiter's attached briefs are the seats' own answers and are passed on as given.

**Run record.** `cli::run` appends one row to the audit's `backtest_runs` (`runs.rs`, migration `3100_backtest_runs.sql`, which replaced #24's never-written table): wall-clock start and end (`SystemClock`, the one wall-clock reading of a run), the archive's SHA-256 and file count, the profiles, and a headline (Predictions and LLM calls per profile, Pick'em Points of finished Stages, Stages, why the LLM track stopped). `audit.backtest_runs()` reads them.

**Reproducing the LLM track.** Answers are kept in the audit's `debate_turns`, which #29's runtime already uses as its cache. `export_answers(&audit)` / `import_answers(&audit, &turns)` move them to and from JSON (`--answers`), so a rerun with the committed `docs/backtest/llm-answers.json` calls no provider and reproduces the report; the report names the archive's SHA-256.

The Major of the direct (real-name) LLM Matches is also shown in detail (`Report::major`): every Match with its format, Scheduled Start, winner and each profile's pick with its probability, marked correct or wrong; and per Stage the Pick'em the solver submitted, each picked team (`three_nil`, `zero_three`, `advance`, or a Playoffs slot) with its record so far and its state (`correct`, `wrong`, `undecided`), and the Points so far.

## Signal Lab (ticket #34, spec #33)

Code: `sidecar/src/adapters/lab/`. Paths below are relative to `sidecar/`. Every Candidate Signal (`GLOSSARY.md`) is evaluated against the anchor (`debate::base`: 0.80 market and 0.20 Valve rating logit, unfitted) under one fixed protocol, over the backtest's replay archive, with no network and no provider. Later tickets of #33 add Candidate Signals; they do not change the protocol.

**Running it.** `cargo run -p kallbet-ai -- lab` (from the repository root) reads `tests/fixtures/backtest/`, writes `report.md` and `report.json` into `target/lab/` and appends one row to `target/lab/audit.sqlite`'s `lab_runs` (migration `3400_lab_runs.sql`; `audit.lab_runs()`: wall-clock start and end, archive SHA-256 and file count, protocol version, seed, `{signal: verdict}`). Options (`lab/cli.rs`): `--archive DIR`, `--out DIR`, `--seed N` (default 33), `--resamples N` (default 2000), `--signal NAME` (repeatable; default every registered one; an unknown name fails and lists the registered ones), `--catch-up-trials N` (default 2000) and `--pickem-simulations N` (default 5000) for the catch-up and Pick'em experiments' own simulations (tests run them small). The report holds no wall-clock time: the same archive and seed give the same bytes.

**Protocol** (`PROTOCOL_VERSION = "signal-lab/4"` in `lab/mod.rs`, `/4` since qualifiers and RMRs (Event name contains `RMR` or `Qualifier`, `runner::is_qualifier`) are neither scored nor fitted on by default (`--include-qualifiers` restores it; their results stay in every history; `report.qualifiers` lists them and carries the secondary with-qualifiers view), `/2` since #37 added the Holdout and the selection, `/3` since a promotion also needs the winners picked not to fall; bump it when any rule below changes, not when a Candidate Signal is added):

- *Point in time* (`signals::MatchView`): each scored Match is read through the replay ports (`backtest::Feeds`: Signal Estimator, Odds Source) at its cutoff (`ReplayMatch::cutoff()`), and each datum is checked with `AsOf::at`; a Candidate Signal returns an `AsOf<f64>` that `Lab::run` checks again. A datum observed at or after the cutoff aborts the run with `TemporalLeakError`.
- *Walk-forward at Event granularity* (`runner::Lab::training`): an Event (PandaScore serie) begins at its first Stage cutoff and ends when its last result became known (`ReplayStage::known_end`: the latest reported `end_at`, forfeits included). An Event with a Stage still in play or a result without a reported finish (`ReplayMatch::known_finish` is `None`: a start time is never taken as a finish, and no finish is estimated) has no known end: it trains nothing, and it is in the Holdout, since its last result may fall after the boundary. A Candidate Signal is fitted once per Event, on every Match of the complete Events that ended before it began, and nothing else.
- *Metrics* (`stats.rs`): on the Matches both the anchor and the variant predicted (paired): mean log-loss (primary, clipped at 1e-6), Brier score, accuracy (team A picked at 0.5). Differences are variant − anchor.
- *Uncertainty*: `stats::event_bootstrap` resamples whole Events with replacement (`SeededRng`, the recorded seed), 90% interval of the pooled log-loss difference; `stats::detectable_effect` = (z₀.₉₅ + z₀.₈₀) × its standard error, the smallest effect those Matches could have detected.
- *Verdict* (`stats::verdict`): fewer than 100 paired Matches → `no evidence`; interval below zero, the paired Matches with a market line not worse on average (or none), and the Event-bootstrap interval of the accuracy difference (variant − anchor, same paired Matches, resamples and seed: `stats::accuracy_bootstrap`, `accuracy_interval` in the report) not wholly below zero → `promote` (KallBet scores only the picked winner); the log-loss interval below zero but the accuracy interval wholly below zero → `no evidence`, "better probabilities but fewer winners picked"; interval above zero → `harmful`; else `no evidence`. `not testable` (with the reason) when `CandidateSignal::missing_data` says the archive cannot have its data, or it was computed on no Match. Every Candidate Signal evaluated is in the report.

**Adding a Candidate Signal.** One file under `lab/signals/`: implement `CandidateSignal` (`name`, `description`, `needs`, optional `missing_data`, `fit(&[Observed])`) and `FittedSignal::predict(&MatchView) -> Result<Option<AsOf<f64>>>` (team A's series probability dated by the latest datum read), then add it to `signals::registry()` (one line). Optional, with defaults: `FittedSignal::parameters()` (what was fitted, shown per evaluated Event in the report), and the combiner features `CandidateSignal::feature_names()` / `FittedSignal::features(&MatchView)` (default one feature `shift` = logit(its probability) − logit(anchor); a signal with raw features, such as rest days, overrides both, one `Option<AsOf<f64>>` per name). A Candidate Signal that needs a datum the view lacks adds the field to `MatchView` and reads it from a port in `Lab::view`, as an `AsOf` checked at the cutoff.

**First Candidate Signal: `rating_calibration`** (`signals/calibration.rs`, story 19): `p′ = sigmoid(s × logit(p_map))` with `s` fitted by maximum likelihood (golden section on [0.01, 4]) on the series results of the training Matches, per format with at least 30 rated training Matches, else the pooled scale, else no prediction; the calibrated map probability goes through `vrs::series_probability` and the anchor's blend.

**Tests.** `tests/lab.rs` (Seam 1, the runner over the saved archive): the calibration's row recomputed from the per-Match predictions (counts, differences, interval from the bootstrap with the run's seed, detectable effect, verdict by the rule); a Candidate Signal returning a datum at, 1 s or 2 h after the cutoff aborts with `TemporalLeakError` (1 s before is accepted), as does a port answering at the cutoff; reversing every result of IEM Cologne 2026 moves no probability of Cologne or any earlier Event and moves Singapore's; a Candidate Signal without data is reported `not testable` with its reason; the subcommand gives byte-identical reports for the same seed and appends each run to the audit store. `tests/lab_stats.rs`: scores, the Event bootstrap on hand-checkable inputs and fixed seeds, the detectable effect, the verdict rule, the calibration's maximum-likelihood scale. Ticket #37: `tests/lab_selection.rs` (learned weights reported with the verdict by the rule and per-Event weights fitted on exactly the earlier Events' Matches; reversing Singapore moves no weight, reversing Cologne only Singapore's; forward selection deterministic, order and gains listed, seed-independent order; a spy shows no fit ever gets a Holdout Match and reversing every Holdout result changes no verdict, selection step or prediction, only the Holdout scores; pending Holdout on the saved archive, a played Singapore Stage 2 is evaluated; the run record's `holdout` column), `tests/lab_combiner.rs` (the combiner without data is the anchor, recovers generating weights on seeded synthetic data, the penalty pulls to the anchor, per-pattern weights; `selection::forward` on a hand-made score).

**Report.** `docs/lab/report.md` and `report.json` are the run over the saved archive (seed 33), rerun with `cargo run -p kallbet-ai -- lab --out docs/lab` (then delete the `audit.sqlite` it leaves there). `docs/lab/research/` is the run over the research archive (ticket #48): its `README.md` has the command, the archive digest, the coverage and the plain reading. The archive is not in the repository. Post-Match Liquipedia bundles of the #36 map collector (`hltv/liquipedia/event-<serie>.json.gz`) are linked to the serie's Stages like `maps-<tournament>` files (`map_history::link_serie`).

**Combiner, selection and Holdout (ticket #37).**

- *Combiner* (`lab/combiner.rs`, pure): `Combiner::fit(extra feature names, &[(Inputs, won)], LAMBDA)`; `Inputs { market, rating (series probabilities), extras (logit-scale features, `None` read as 0) }`. Logistic, no intercept, one weight vector per availability of the anchor's inputs (`Pattern::Both` market+rating, `MarketOnly`, `RatingOnly`), each fitted by Newton's method with the penalty `LAMBDA/2 · |w − w₀|²` (`LAMBDA = 10`), `w₀` = the anchor's weights (0.80 / 0.20; 1 alone; 0 for extras). No training Match → exactly the anchor. `parameters()` gives the weights and Match counts per pattern.
- *`learned_weights`* (`signals/learned_weights.rs`, story 20): the combiner over market and rating only, a Candidate Signal like any other; its per-Event weights are in the report's per-Event table.
- *Holdout* (`lab/holdout.rs`, `Lab::holdout`): a Stage is in it when it begins at or after spec #33's publication (`SPEC_PUBLISHED`, 2026-11-25 23:46:46 UTC) or its Event has a result at or after it, except `SINGAPORE_STAGE_1` (PandaScore 22378, training side by the spec). `Lab::events` splits the archive: per-signal evaluation and selection get only the training side; Holdout Events (a Holdout Stage's Event, e.g. Singapore's later Stages, forms its own Event) go only to `selection::holdout`. Tests move the boundary with `lab.holdout = Holdout { from, training_stages }`.
- *Order of work* (`Lab::run`): every Candidate Signal alone (as before); then `selection::select` on those marked `promote`: greedy forward selection (`selection::forward`, pure; ties to registry order; stops when no candidate lowers the walk-forward log-loss), each tried combination = the combiner over market, rating and the members' features, refitted for every training-side Event on the Events that ended before it, with each training Match's features taken from the member's fit for that Match's own Event (out of sample). Start: the anchor. The report lists the order, what each entrant added (log-loss after − before) with its Event-bootstrap interval, and the combiner's weights per Event. Then the frozen combination on the Holdout, once: for each Holdout Event the members are fitted on the training-side Events that ended before it, the combiner likewise; nothing promoted → the anchor itself. `report.holdout`: status `pending` (no Holdout Match played: the run still completes) or `evaluated`, the statement of when (the evaluation date, `holdout.evaluated_at`: the start of the first CLI run that evaluated it, which a reproduction keeps, so the same archive and seed still give the same bytes; final step of the run, after the freeze, dates of the Holdout Matches; the `lab_runs` row's `holdout` column says `pending` or `evaluated: <members>`), the metrics against the anchor with interval and the rule's verdict, the combiner's weights. `LabOutcome::{combination, holdout}` hold the per-Match predictions. *Single use* (`Lab::freeze`, `holdout::Freeze`): the CLI reads the first `lab_runs` row whose `holdout` is `evaluated: …`; a later run that would evaluate a played Holdout is refused before it reads a Holdout Match unless its archive SHA-256 and frozen combination are the recorded ones (a reproduction). Keep `audit.sqlite` with the reports it belongs to.

**`rank_gap` (ticket #57, added after the list was fixed).** `MatchView::ranks` (`backtest::rank_history::Ranks`) holds both teams' VRS rank (the latest dated Valve standings strictly before the cutoff) and HLTV world rank (the HLTV match page badge, dated by the weekly ranking it links to, known once that UTC day is over, at most 35 days old, never from a hidden Match's page). The page's VRS badge is never read: the audit in `docs/signal-lab/criteria-research.md` (C1) found it already holds the Match's own result. The signal is the combiner over market, rating and the two log rank gaps (`vrs_rank_gap`, `hltv_rank_gap`, also its combiner features), fitted on the training Matches with a gap.

**Not done here.** The history store; the archive is the backtest's small saved one, on which nothing is marked `promote` yet (so the frozen combination is the anchor and the Holdout is pending).

**Promotion to a live bot (ticket #47).** Code: `src/promotion.rs`; config `Policy::Promoted { name, report }`; `Sidecar::from_config` loads it per bot (`registry.rs`) into `Sidecar::promotions`; the scheduler (`Sidecar::predict`) decides for such a bot itself, without the LLM or `ConfiguredPolicy`.

- *What the lab writes*: `LabReport.deployment` (`report.json` only; the Markdown is unchanged) holds, for every `promote`d Candidate Signal that can run live, its fit on every training-side Match at full precision (`FittedSignal::deployment()`, default `None`), and under `combination` the frozen combination's `Combiner` fitted like the Holdout's (`selection::deployment_combiner`). `Combiner`, `Calibrated` and `Learned` are serde types for this.

Either way the tick goes on. (label = the signal, or the members joined by " + "), or "No live data for the Signal Lab criterion `<label>` (`<reason>`, English only): the anchor decided."

## LLM track of the Signal Lab (ticket #43, spec #33)

Code: `sidecar/src/adapters/lab/llm.rs`. The single agent and the three-seat debate, under every Seating the operator lists, on every archived Match with a roster flag, each compared with the anchor by the lab's own runner; the debate's adjustment is the Candidate Signal `llm_adjustment`.

**Running it.** `cargo run -p kallbet-ai -- lab --archive DIR --llm FILE --answers FILE --budget claude=RUNS --budget codex=RUNS --budget antigravity=RUNS` (one `--budget` per provider of the file; RUNS is the operator's choice; `--llm` without an explicit `--archive` is refused, since the default archive is the small test one). `--llm FILE` is JSON `{"llm": <the sidecar config's llm section>, "single": [provider...], "seatings": [{"name", "advocate": [...], "devil": [...], "arbiter": [...]}...]}` (sample `docs/lab/llm.example.json`: the three rotations of Claude, Codex and Antigravity). `--answers FILE` holds the recorded answers (`Recorded`: the seatings, the single agent's turns, each seating's debate turns); it is read first and rewritten after the run. With `--answers` alone no provider is configured and nothing can be called: the tables are rebuilt from the recordings. `--training-cutoff RFC3339` (default `2026-11-01T00:00:00Z`): Events that began before it go through the BlindAnonymizer. Output: `llm.md` and `llm.json` next to `report.md` (which links `llm.md`), one audit file per seating in `llm-audit/`. Without `--llm` and `--answers` the track is not run, `llm_adjustment` is `not testable` and `llm.md` gives the command.

**Spending.** `programs` checks before anything runs: providers named but no `--budget` → refused ("refusing to call any provider"), a provider without its own `--budget` → refused, an `http` provider → refused (only CLI runs are budgeted), two providers on one CLI binary → refused (a budget is per subscription). `Budgeted` (a `ProcessRunner` wrapper) counts runs per provider by the invocation's program and refuses the run past the budget with `RunError::OverBudget`, which `CliRuntime` maps to `LlmError::QuotaExceeded`: the backtest runner then stops that seating's LLM profiles (a fallback in the seat's chain is used instead, as live). A real quota or sign-in failure stops the whole track at once: `Budgeted` reads each run's output with its CLI's parser and, after the first `QuotaExceeded` or `Auth`, starts no run of any provider (not the Arbiter after a failed Advocate, not a fallback provider of a seat's chain), and later seatings are `not run`. The report lists budget, runs used and runs refused per subscription, what each profile lacks, and the command with `<RUNS>` placeholders.

**What runs.** Per seating, `Backtest` (the backtest's live pipeline, `Mode::Backtest`: no tool and no web whatever `web_search_bots` says; `Blind` with the archive's known names for the blind Matches; `Required`) over the Stages that hold a flagged Match, in a fresh audit file with the single agent's and that seating's recorded answers imported (the debate's reuse key does not name the provider, so seatings never share an audit). *Flagged*: a Match whose `ReplayContext` facts at `cutoff − 1 s` hold a `liquipedia_roster` with `has_stand_in` for either team (57 in the saved archive: Shanghai 2024 and Cologne 2026 blind, 3 of Singapore Stage 1 with real names).

**Evaluation.** `LlmAnswers` is a Candidate Signal over recorded probabilities (nothing fitted; each dated `cutoff − 1 s`). `Track::adjustment()` (the first seating's debate) replaces the registered `llm_adjustment` before `Lab::run`, so it gets its verdict by the same rule as every Candidate Signal. `compare` swaps `lab.signals` for `Track::profiles()` (`llm_single`, `llm_debate_<seating>`), runs the same `Lab::run`, restores them, and adds the debate − single agent log-loss with the Event bootstrap. With 57 flagged Matches the verdict is `no evidence` whatever the estimate (floor 100).

**Tests** (`tests/lab_llm.rs`, scripted `ProcessRunner` answering with the saved CLI outputs of `tests/fixtures/debate/`): the flagged set and blind split; no budget or a provider without one refuses before any run (library and subcommand); a spent codex budget: exactly that many codex runs, the seating stops, the next seating completes, counts in the report; Antigravity's saved quota error: one run, the next seating not run, the lab's other Candidate Signals still evaluated, `llm.md` lists what is missing and the command; a rerun from recorded answers with no provider and no budget starts no process and gives equal tables; every profile's verdict equals `stats::verdict` on its numbers and `llm_adjustment` equals the first seating's row; every CLI run's no-tools argv with both profiles in `web_search_bots`, and every blind prompt (Arbiter's attached briefs included) free of the blind Events' teams, players, coaches, titles and years; the subcommand replays `--answers` and writes `llm.md`.

**Not done / limits.** The real run is the operator's (no provider was called while building this). "Roster flag" is a stand-in only: the replay has no dated roster-change feed (ticket #39's `roster_change_30d` reads Valve's rosters; a later ticket can widen `flagged`). The seating's replay holds only the Stages with a flagged Match, so the anonymizer knows the teams of those Stages and every team, player and coach of every saved Liquipedia revision, not PandaScore names of the other Stages (the archive has no free-text news that could name them). A Holdout Match has LLM answers only if it is flagged and the track ran on an archive that holds it.

## Known limitations

- **A local duplicate next to a stored HLTV Match is not merged.** Adoption (`mapping::adoptions`) only re-keys a local Match to an HLTV id that is not stored yet (`rekey_match` refuses an existing target). Since B1, a local Match whose two teams HLTV shows in the same Swiss or Playoffs Stage is adopted whatever the time; but in a Groups Stage (where a pair can meet twice) a local Match HLTV first publishes outside the matching window stays a separate local Match, with its Predictions, next to HLTV's. A League Admin can hide one with an Override. Merging two stored Matches (Predictions, Lock/Reveal stamps, Overrides, notification keys) is not implemented.
- **HLTV live Swiss round markup is unverified.** The parser leaves out a Swiss Match drawn in the chart but in neither team's standings rows (A13), tested on a variant derived from a real page. No real page of a Swiss Stage with a live Match has been saved, so how HLTV really draws that state is not confirmed.
- **Stage ordinal moves need a shared Match.** `move_stage_data` (B2) infers how ordinals moved from stored Matches that the new snapshot places in another Stage. A Stage whose stored Matches HLTV does not show (all still local and not adopted) keeps its ordinal, and its Pick'ems with it.

**Pick'em variants (ticket #46).** `lab::pickem::run(&lab, &PickemOptions)` scores every completed Stage of the archive outside the Holdout: `baseline` (the live solver: market for opening pairs, Valve's rating otherwise), `calibrated` (`rating_calibration`), `learned` (`learned_weights`), `variance_seeking` (baseline, but when the bot trails the simulated Members on the Pick'em Leaderboard the baseline's own picks are worth less, via `pickem::Avoid`). Pick'em Points are `backtest::report::pickem_points`; the difference from the baseline is the mean Points per Stage with `stats::event_bootstrap`; `pickem::verdict` has a floor of 10 Stages. Every submitted payload passes `validate_payload`, and the solver rejects a view with a result or a later-round pairing (`TemporalLeakError`). The `lab` command writes `pickem.md` and `pickem.json` next to `report.md`. A new rating source for the solver is one more entry in `candidates` in `run`.
